# 多轮 Skill 挖掘与人工补证

控制台的 Skill 挖掘由 teamEvolver 管理真实轮次，每轮由 TE 分批调用现有 OpenViking Compile。新任务先规划可独立执行的任务方法，再编译为一组 Skill Candidate。启用人工补证时，上一轮结束后任务暂停，管理员复核本轮候选集合、回答 Evidence 缺口并补充来源，再启动下一轮。

这条流程使用 OpenViking 上的模型和执行环境；控制台全局模型设置不决定本轮 Compile 使用的模型。原始知识源只在任务开始时冻结，之后修改源目录不会悄悄改变任务输入。

首轮从冻结的原始来源确定并保存主要语言；中文主导的材料使用简体中文。各轮的候选正文、评估说明、案例 Query、Checklist 自然语言、共享分析和复核问题沿用该语言，不受旧英文产物或后续补证语言影响。字段名、ID、文件路径、来源 URI、代码、固定枚举和原文直接引用保持原样；`Checklist`、`Evidence`、`Materials` 等结构标签也保留原样。

控制台没有独立的输出语言选择器。运行时将任务语言规则加入新的 Compile 请求，保存的自定义业务编译指令保持原样，无需重置。已受理请求的冻结内容和已完成产物不追溯修改，也不会因语言规则更新而自动翻译或重新 Compile。

## 创建任务

在知识源页面选择带有 Skill 用途标签的目录，然后创建 Skill 挖掘任务。

| 设置 | 行为 |
| --- | --- |
| 最大挖掘轮数 | 1–5，默认 3；每轮保留独立输入、产物与分阶段 Compile 记录 |
| 人工补证 | 启用后，每轮完成进入人工复核，包括最后一轮 |
| 每轮运行期限 | 基础期限 60–7200 秒，默认 3600；默认契约按输入分片和产物工作量延长实际期限，不计算等待人工回复的时间 |

关闭人工补证后，teamEvolver 自动执行设置的轮数。各轮仍保留独立输入、产物和执行记录。最多同时执行 8 个 Compile 挖掘任务；等待人工补证的任务不占执行名额。

## 能力拆分与候选集合

模型根据任务的触发场景、输入、输出和边界决定候选数量。一个候选必须能独立执行，也能独立通过 True Replay 验证；文档篇数、章节数或主题数不决定数量。同一份文档可以支持多个方法，一个方法也可以引用多份文档。重叠方法应合并，完整流程中不能独立使用的步骤应保留在同一个候选内。

每个有界规划任务最多输出 8 个候选，整轮可通过更多任务处理更多有效方法。模型不需要凑够数量；只有事实或 Evidence 不足时，可以不生成候选，并说明原因。方法提议有逐项处置记录，事实信息不会自动成为补证问题。编译结果是待验证的 Skill Candidate 集合，经过各自的门禁后才进入已有 Skill 库。

先查看共享的 `analysis/capability-plan.json`（`schema_version: "skill-miner.plan.v1"`）。其 `skills` 条目说明 `name`、`task`、`trigger`、`inputs`、`outputs`、`boundary`、`rationale` 和 `source_refs`；`deferred` 条目保留暂缓内容的 `reason` 与 `source_refs`。这份计划解释哪些方法分开、哪些合并，以及哪些来源仍不足以支持可执行方法。

默认分批流程另生成 `analysis/method-dispositions.md` 和 `analysis/dispositions/page-0001.md`、同名 JSON 等分页。它们逐项说明方法提议如何保留、合并、归为事实信息或暂缓，保留来源及原因。事实信息不自动触发人工补证。

每轮共享四个分析文件：`evidence-map.md`、`gaps.md`、`review.json` 和 `capability-plan.json`。每个候选在 `compiled_skill/<skill-name>/` 下有自己的 `SKILL.md`、`EVALUATION.md`、`BENCHMARK.md` 和 `benchmark.json`。后者是候选专属的 Test Dataset。零候选轮次只保留共享分析，需要继续补证或结束任务，不能提交候选。

控制台按 Skill Candidate 分组浏览产物。每张卡片包含能力说明、该候选的结构校验结果和四个文件；共享分析、暂缓内容与任务级 Evidence 问题单独展示。历史轮次采用相同分组，只读查看。结构校验通过不代表业务事实正确，也不代表已经通过 True Replay。

已有任务保持原来的单候选和七文件契约，恢复或继续不会自动切换。使用当前默认编译 Skill 的新任务采用多候选契约。如果之前保存的自定义编译 Skill 仍使用单候选契约，系统会提示兼容性警告，并继续按单候选执行；在挖掘设置中重置为当前默认编译 Skill 后，新建任务才启用能力拆分。

候选分别接受包与 Test Dataset 的结构校验。某个候选缺少 `SKILL.md` 或其他必需文件时标记为产物不完整，不能提交；其他完整且结构合格的候选仍可进入后续流程。

## 复核与补证

每轮完成后，控制台展示本轮产物和结构化问题。问题来自 `analysis/review.json`，与 `analysis/gaps.md` 中的 Evidence 缺口对应。每个问题有独立标识、问题说明、需要补证的原因、来源引用和是否必答。

1. 查看能力拆分计划，逐个检查候选的 `SKILL.md`、`EVALUATION.md`、`BENCHMARK.md` 和 `benchmark.json`。每个 `benchmark.json` 是统一 `team-replay.dataset` 格式的 Test Dataset，包含 12–24 个案例，用于该候选的 True Replay。
2. 对问题填写回答，可填写有权访问的 OpenViking 来源引用。无法确认的问题应明确标记为未解决。
3. 按需要上传补充文档，并填写对本轮产物的复核意见。附件先保存在任务本地目录；点击继续之前不会写入 OpenViking。
4. 点击继续后，teamEvolver 冻结下一轮输入并启动新的 Compile。达到轮数上限时，只能完成最终复核或结束任务。

初次产物同步时，系统从结构合格的 `benchmark.json` 确定性地规范化已经生成的 `BENCHMARK.md`，保证展示的案例、Checklist 和来源与 Test Dataset 一致，不额外编造案例或事实。缺失必需文件的候选仍需修复，不会通过规范化补齐文件。

问题清单为空时，启用人工补证的任务仍等待人工确认，管理员可以直接继续或结束。浏览器刷新或服务重启不会丢失等待状态和已保存附件。

## 下一轮输入

每轮输入包含三个职责清楚的部分：

- **原始 Evidence**：任务开始时冻结的知识源快照。
- **人工补证**：累计回答、来源和补充文档，并保留提交人和时间。
- **修订上下文**：上一轮各 Skill 正文、Test Dataset 的案例标识及本轮复核问题和意见，帮助模型修订候选集合。

来源抽取及产物生成阶段的 `from` 只包含按预算固化的原始 Evidence 和人工补证文本片段；规划阶段使用可追溯的方法账目，不把模型摘要当作原始事实。修订上下文以已提供的引用文本放入 `instruction`，不会作为来源文件重新执行提取，也不能用于 provenance 引用。完整的上轮共享分析与各候选产物仍保存在本地轮次归档中；不把完整 Test Dataset 和重复 Markdown 内容再次放入提取输入。

默认分阶段流程将上一轮候选身份、案例标识和来源范围保存在本地修订账目中。每次模型任务只接收与当前来源范围或候选名称匹配、能容纳在该任务预算内的修订上下文；节选和省略有明确标记，完整内容仍保留在归档中。自定义单次 Compile 的修订上下文 JSON 保持 30000 字符上限。节选不意味着要求模型使用工具寻找剩余文件。

方法范围稳定时，下一轮显式复用既有候选身份及其案例标识；程序保留身份字段，扩展对应的来源范围。相似但不同的方法需要独立保留，不能仅因名称或共享来源接近就合并。暂缓提议必须回查相关原文，只有确认必要规则仍缺失时才形成补证问题；上一轮产物不能用于证明规则存在。

上一轮模型产物不作为已证实的 Evidence。模型必须引用原始来源或人工补证来源；人工回答与原文冲突时应保留冲突，不以新回答自动覆盖原文。

每轮使用独立输出目录，避免上轮文件遗留。控制台保留各轮的远端任务 ID、输入引用、产物、校验结果和耗时，可查看不同轮次的结果。

## 结束与后续验证

在人工复核阶段可以提前结束；最后一轮也需要完成最终复核。结束时可保存复核意见和未解决的问题。若还有 Evidence 缺口，最终候选集合保留“需复核”提示。

最后一轮完成后补充的内容不会自动修改本轮产物；需要把这些内容纳入产物时，应在尚有轮数时继续挖掘，或创建新的任务。结束挖掘不会自动 Publish。管理员选择具体候选，连同它自己的 Test Dataset 提交；每个 Skill Candidate 分别进入现有 True Replay、Candidate Review 和 Publish 流程，保留独立的状态与结果。

Test Dataset 结构校验确认文件契约正确，不证明业务事实、数值比较或回答条件正确。多轮补证提供修订机会，管理员仍需检查来源与产物是否一致。

OpenViking 的 `completed` 也可能表示部分来源处理失败后保留了可用产物。即使共享分析和各候选的必需文件齐全且格式通过，也不能据此认定所有 Evidence 已被处理。控制台在人工复核、轮次历史和最终产物质量中保留这类警告，并将当前产物标记为“需复核”。例如，一份源文档提取失败时，另外两份文档仍可能生成完整的候选集合。

遇到来源遗漏时，应检查警告涉及的文档并补充复核意见；继续下一轮会重新处理完整的原始冻结知识源和累计补证。上一轮候选仍只是修订上下文，不能代替漏处理的原始 Evidence。后续轮次的结果需重新检查，历史警告保留在对应轮次记录中。

## 恢复与停止

teamEvolver 在本地持久化轮次、人工复核和提交状态。服务重启后恢复现有轮次的远端状态，不重复创建已受理的 Compile。网络中断导致受理结果未知时，使用同一阶段原有的幂等键查询或恢复提交。

每轮首次准备时还会冻结本轮编译 Skill 正文和输入归档。编译器安装到名称包含来源正文摘要的独立 Skill URI，记录 `compiler_source_sha256`、实际安装正文的 `compiler_sha256` 和 `compiler_uri`。已存在的版本仅在正文一致时复用，内容冲突会停止提交，不覆盖该版本。

同一阶段重试使用相同的编译器 URI、正文、输入和 Compile 请求；阶段产物校验完成后才提交下一阶段。受理结果未知且远端尚未记录任务时，可以用已冻结正文恢复缺失的编译器包；已记录任务则直接恢复状态。服务更新或其他任务安装新编译器，不会改变本轮绑定的版本。

停止执行中的任务会请求 OpenViking 协作取消，等待远端终态。人工等待阶段可以直接结束。删除任务前应先停止正在执行的任务。

接口和错误说明见 [Skill 挖掘 API](../api/17-skill-mining.md)。实现位于 [任务仓库](../../../team_miner/ov_compile_mining.py) 和 [主服务桥接](../../../team_miner/bridge.py)。
