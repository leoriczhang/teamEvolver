# Installation

teamEvolver installs in two ways: developers install from the source tree, delivery environments install offline from an immutable release. Both install the same set of Python packages (`teamEvolver`, `session_ingestion`, `team_skills`, `team_replay`, `team_memory`, `team_miner`).

## Requirements

| Component | Version | Notes |
|------|------|------|
| Python | 3.11 (minimum 3.10) | The release image is `python:3.11-slim-trixie` |
| PostgreSQL | 14+ | The application role must be NOSUPERUSER, NOBYPASSRLS |
| OpenViking | Compatible Content, Session, Search and Compile APIs | Authority for knowledge artifacts; the container ships a pinned `ov` CLI |
| Node.js / npm | 20+ | Only for building the console |
| Docker | BuildKit | Builds the release and image |
| uv | Any recent version | Only for regenerating lock files |

## Dependency Sources

- `pyproject.toml` is the single source of direct Python dependencies and has one extra, `dev`.
- `requirements.lock` (runtime) and `build-requirements.lock` (build tools) are generated by `scripts/lock_dependencies.sh`; every package carries a SHA-256 and the locks cover CPython 3.11 on Linux amd64/arm64.
- Rerun `scripts/lock_dependencies.sh` after changing `pyproject.toml`.

## Development Install

```bash
bash scripts/install_teamEvolver.sh            # optional --venv-dir, --python
bash scripts/install_teamEvolver.sh --apply-schema   # also runs schema apply (needs TEAMEVOLVER_PG_DSN)
source .venv/bin/activate
```

Script steps: create the venv → `pip install --require-hashes -r requirements.lock` → `pip install --no-deps -e .` → install development tools such as ruff and pytest → `pip check`.

Console sources are in `web-ui/`; the build output goes to `teamEvolver/web/dist/` and is packaged into the wheel:

```bash
npm --prefix web-ui ci
npm --prefix web-ui test
npm --prefix web-ui run build
```

## Build a Release

```bash
TARGET_ARCH=x86_64 sh cicd_scripts/build.sh     # or TARGET_ARCH=aarch64
```

Build order:

1. Frontend `npm ci`, tests and production build (`SKIP_FRONTEND=1` reuses existing output).
2. Download a hash-verified wheelhouse for the target image's interpreter version and manylinux architecture; dependencies published only as sdist keep the locked sdist.
3. Build the application wheel inside the runtime image with `--network none`.
4. Generate `release/manifest.json` (version, target image digest, schema version and SHA-256 of every file) and pack it as `app.tar`.

```text
release/
├── teamevolver-<version>-py3-none-any.whl
├── wheels/
├── requirements.lock
├── build-requirements.lock
├── install.sh
├── container_start.sh
└── manifest.json
```

## Offline Install

```bash
mkdir -p /app/deploy && tar -xf app.tar -C /app/deploy
python3.11 -m venv /opt/teamEvolver-venv
PYTHON_BIN=/opt/teamEvolver-venv/bin/python sh /app/deploy/install.sh
```

`install.sh` first verifies every file against the manifest, then installs build tools, dependencies and the application wheel with `--no-index --require-hashes`, and finally runs `pip check`. The install needs neither network nor the source tree.

`scripts/verify_offline_install.sh [app.tar] [linux/amd64|linux/arm64]` verifies this flow in an empty container with `--network none`.

## Container Image

```bash
TARGET_ARCH=x86_64 sh cicd_scripts/build.sh
docker build --platform linux/amd64 -t teamevolver:<version> .
```

The Dockerfile only does `COPY release/`; it copies no source and sets no `PYTHONPATH`. The image ships the OpenViking CLI at a pinned version and checksum and installs `git` (used only by Skill Git import/export). The entrypoint is `container_start.sh` and requires `TEAMEVOLVER_ROLE=api` or `worker`. Deployment is described in [Production Deployment Guide](../guides/02-deployment.md).

## Initialize the Database

```bash
export TEAMEVOLVER_PG_DSN="postgresql://te_app:...@db:5432/teamevolver"
teamEvolver schema apply --dry-run   # list pending versions
teamEvolver schema apply
teamEvolver schema status
```

The schema (default `teamevolver`, changeable via `TEAMEVOLVER_PG_SCHEMA`) must be created in advance by an administrator and owned by the application role. `schema apply` is idempotent and records runs in `schema_versions`. Business modules do not create tables at runtime.

## Start and Manage

```bash
teamEvolver start --role api       # HTTP API + console, default port 52010
teamEvolver start --role worker    # Worker + health port, default 52011
teamEvolver start --role all       # TEAMEVOLVER_ENV=local only
teamEvolver start --role api --daemon --log-file /var/log/te-api.log
teamEvolver status
teamEvolver stop
```

## Verify the Install

```bash
curl http://localhost:52010/healthz      # liveness
curl -i http://localhost:52010/readyz    # readiness; 503 when PG is unavailable or draining
curl -i http://localhost:52011/readyz    # Worker readiness
teamEvolver config show                  # redacted bootstrap configuration
python -m pytest                         # for source installs
```

## Upgrade

1. Build the new release, run the offline install and `teamEvolver schema apply --dry-run` in pre-production.
2. Run `teamEvolver schema apply`. The schema only moves forward; application rollback can only go to a release compatible with the current schema.
3. Replace API and Worker instances one at a time. On SIGTERM an instance first withdraws readiness, then waits for in-flight tasks to finish.
