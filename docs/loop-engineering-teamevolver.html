让 Agent 从真实工作中进化：
teamEvolver 的外层循环与 True Replay

从会话中提炼技能并不难，难的是证明新技能真的更好。teamEvolver 将经验筛选、候选生成、隔离回放、发布判断和版本回流组织成一个可审计的持续进化闭环。

一个 Agent 完成了任务，并不意味着系统已经学会了这项能力。经验可能只存在于某次对话里，可能依赖某台机器上的文件，也可能是一条看起来合理、实际会让工具调用退化的流程。要把经验变成团队资产，需要一个比“总结这段会话”更严格的系统。

teamEvolver 的目标，是把真实 Agent 使用经验沉淀为可复用、可同步、可验证的 SKILL.md。它位于 Agent Runtime 外层，不直接替代 Agent 的执行循环，而是观察大量已完成会话，提出改进候选，再通过对照实验决定是否发布。

生成技能几乎是免费的，可靠判断却仍然昂贵。外层循环真正稀缺的资源不是文本，而是可信的验证。

01 · The problem为什么“自动总结经验”还不够

最朴素的技能演进流程是：读取成功会话，让模型总结一套步骤，然后覆盖原技能。这条路径有三个严重问题。

首先，它把生成者和验收者合并为同一个角色。模型通常能解释自己的候选为什么合理，却无法证明它在真实环境里更有效。其次，最终回答掩盖了行动过程：一个技能可能输出更漂亮的文字，却多调用三次工具、遗漏一个关键文件，或者产生真实副作用。最后，线上技能一旦被直接覆盖，就失去了 baseline，对未来退化也缺乏可回滚依据。

teamEvolver 的基本约束：候选不能因为“看起来更完整”就发布。它必须在相同任务、相同环境与相同预算下，与当前版本进行 A/B 回放，并留下可审计的分支轨迹。

02 · Two timescales内层完成任务，外层改进能力

AgentsHub 和 teamEvolver 形成两个不同时间尺度的循环。内层执行环在秒到分钟内收敛，目标是完成当前任务；外层进化环在小时到天的尺度上收敛，目标是提高未来相似任务的成功率。

把两个循环分开有一个直接好处：运行时反思不会在一次任务中擅自修改团队技能；技能演进也不能绕过隔离验证直接影响线上 Agent。人的位置从每一步执行，移动到高风险发布和证据冲突的判断点。

03 · Evidence pipeline一段会话如何成为可验证证据

teamEvolver 接收的不只是聊天文本。AgentsHub 导出的原生会话包含每轮 prompt / response、工具调用和结果、已注入与实际使用的技能、每轮前后状态、附件、Agent / Environment / Model 身份，以及 input、output、cache 和 reasoning Token。

证据层关键内容验证价值
Conversation用户目标、回答、历史回合恢复任务语义与多轮上下文
Trajectorytool calls、tool results、AgentEvent判断任务是否真的通过工具完成
Capabilityinjected skills、used skills识别能力来源和技能缺口
RuntimeAgent、Environment、Model、session state恢复执行身份与状态边界
Filesystem附件与 sandbox tar.gz 快照让回放看到原任务使用的真实文件
Efficiency交互、工具数、Token、延迟判断候选是否用过度消耗换取质量

先判断会话是否值得学习

SessionValueClassifier 先区分高价值任务和闲聊。工具调用、实际使用技能、具体操作流程和任务产物是强信号；没有配置分类模型时，系统按内容复杂度、工具和技能使用做启发式降级，并把判断写入审计记录。

候选不是发布版本

有价值会话进入共享对象存储，候选技能和验证任务分别持久化。候选拥有自己的 job ID、来源 session、当前技能、建议动作、回放案例和最低分数。直到验证决策完成，它都不会替代现有技能。

04 · True Replay为什么必须回放行动轨迹，而不只比较回答

普通文本 A/B 只能比较最终回答。True Replay 则同时启动 baseline 和 candidate 两个隔离分支，让它们在同一任务、同一环境和相同预算下运行完整 Agent Loop。两条轨迹最终交给独立 Judge，判断任务完成度、工具正确性和整体质量。

AgentsHub 原生回放会对 SQLite 数据库做一致性备份，为每个分支创建独立子进程和全新数据目录，恢复来源会话状态与沙箱快照。在线记忆、远程 Viking 能力和会话再次上报会被关闭，避免回放污染真实系统。

true_replay.py · conceptualPython
branches = {
    "baseline": current_skill,
    "candidate": proposed_skill,
}

# 同一来源会话，同一 instruction，同一环境快照
results = parallel_run(
    branches,
    source_session=source_session,
    sandbox_snapshot=snapshot,
    tool_cassette=recorded_results,
)

scores = strict_judge(results)
accepted = (
    scores.candidate >= 0.75
    and scores.candidate >= scores.baseline - 0.15
    and efficiency_delta >= -0.10
)

副作用如何被隔离

回放中的工具调用不应再次发送邮件、修改订单或触发外部写操作。AgentsHub 使用 cassette executor 消费原轨迹中记录的工具结果；没有可用记录时返回 REPLAY_TOOL_MISS，而不是访问真实业务系统。

这是一种保守设计：它牺牲部分动态真实性，换取可重复和无副作用的验证。对于只读查询，未来可以逐步引入受控实时回放；对于写操作，仍应坚持 cassette、沙箱或专用测试环境。

05 · Release gate发布门禁如何判断“真的更好”

teamEvolver 的门禁不是一个单分数阈值。它同时检查绝对质量、相对回归、效率和分支完整性。这可以避免两类常见错误：候选比一个很差的 baseline 稍好，但仍不可用；候选质量略有提升，却消耗显著更多 Token 和工具调用。

门禁维度当前规则设计目的
绝对质量candidate overall ≥ 0.75保证候选本身达到可用标准
无明显回归candidate ≥ baseline - 0.15容忍评估噪声，拒绝实质退化
相对价值质量不低于基线，或效率提升要求候选带来至少一种真实收益
效率底线综合效率退化不得低于 -10%防止用无限资源购买轻微质量
硬失败任一分支失败则拒绝证据不完整时不自动发布

自动门禁并不取消人工判断。高风险技能、新型副作用、Judge 冲突和强制发布仍进入候选评审。人工评审看到的不是一句“建议发布”，而是技能 diff、两条轨迹、Judge 理由、质量与效率明细。

06 · Distributed validation为什么验证可以分布到空闲客户端

ValidationWorker 在共享开启、客户端空闲且每日配额允许时领取开放任务。验证结果按 job 和 user alias 写入共享存储，进化服务可以要求多份结果和多票通过，再决定发布或升级人工。

这使验证能力可以复用团队机器的空闲资源，也避免中心服务承担所有模型与回放成本。默认配置仍然保守：单客户端每日最多 5 个任务、并发 1，只有在空闲时间达到阈值后才运行。

01 / SEPARATE生成与验证分离

候选生成上下文不能直接决定自己的发布结果。

02 / PERSIST任务与结果持久化

job、result、decision 和 human review 都是共享状态。

03 / BUDGET验证也有预算

空闲阈值、每日配额、并发和超时共同约束成本。

04 / REVERSIBLE发布必须可逆

版本记录与 rollback 让错误学习不成为永久状态。

07 · Honest gaps当前实现还不够完整的地方

Loop Engineering 的价值来自真实边界，而不是架构图的完整。当前系统已经具备外层循环骨架，但仍有四个重要缺口。

AgentsHub 原生回放仍是单轮

回放请求暴露了 max_interactions，Hermes 路径也支持根据 Judge feedback 继续交互；但 AgentsHub 原生 worker 当前只执行一次 handle_turn。两种运行时的完成语义需要统一。

工具 cassette 的匹配粒度不足

当前主要按工具名和顺序消费记录。同名工具多次调用、但参数不同的会话可能错误配对。更可靠的键应包含工具名、规范化参数、资源 ID 和 occurrence index。

沙箱快照依赖同机路径

tar.gz 快照恢复了文件保真，但来源路径仍是同机绝对路径。跨机验证需要把快照改为带摘要、权限和生命周期的对象存储资源。

Judge 仍需校准

评估角色已经分离，但可能仍使用相同模型族。下一步应组合硬校验、异构 Judge、规则评分和固定比例人工抽检，并版本化 rubric、模型和阈值。

08 · Roadmap从技能演进走向循环演进

短期优先级不是增加更多自动化，而是提升证据质量。首先统一 stop reason 和 Loop Contract；随后补齐原生多轮回放、参数级 cassette 与跨机快照；再建设按技能分层的固定回归集、灰度发布与自动回滚。

只有当这些门禁稳定后，外层循环才适合扩展优化对象：从 Skill 进一步覆盖 Prompt、Context policy、Tool schema 和 Harness 配置。每一种对象都必须拥有独立的权限、评测集和回滚方式，否则一次变更多层会让失败无法归因。

可靠的自我改进，不是让系统更快地修改自己；而是让每次修改都能被复现、比较、拒绝和撤销。

这正是 teamEvolver 对 Loop Engineering 的实践答案：把真实工作变成证据，把候选变成实验，把发布变成可审计决策。Agent 因此不是在一次对话中“突然变聪明”，而是在长期运行中，通过受控反馈逐步积累组织能力。
