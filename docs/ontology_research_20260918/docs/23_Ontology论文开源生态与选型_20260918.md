# Ontology 论文、开源生态与顺丰选型研究

> 2026-09-18｜研究快照；不是系统上线或性能验收报告。与24号领域蓝图、25号完整方案V3、26号接口验收册配套。本文的 Ontology 指业务语义建模，不指同名区块链产品。

## 1. 结论与选择

建议采用 **teamEvolver 本体工程工作台 + OpenViking Compile 执行链 + OV 结构化 Ontology 服务**。本体模型和构建方法借鉴 HugAgentOS、OntoGPT、LinkML、Graphiti 与语义网标准，不另建一个 HugAgentOS 业务主平台，不新增第三套权威知识库。

选型依据不是“谁有图”，而是能否把有版本的业务概念、适用条件、证据、规则和工具契约，变成 Agent 可查询、可解释、不可越权的上下文。下面将论文结论、项目文档声明与本方案推论分开；没有将其他行业的数据集成绩转换为顺丰效果承诺。

## 2. 六项值得吸收的论文工作

| 工作／阅读范围 | 核心贡献 | 对顺丰的取舍 |
| --- | --- | --- |
| LLMs4OL，ISWC 2023；论文摘要、任务定义与仓库说明 [P1] | 分别研究术语类型识别、上下位关系和非分类关系；不同任务、领域表现不一 | 分开评测“识别实体”“类型归类”“关系正确”“限定条件完整”，不以一个抽取准确率概括本体质量 |
| SPIRES，Bioinformatics 2024；预印本摘要、发表元数据及 OntoGPT README [P2] | 根据结构化模板递归抽取，并将名称落到可识别的术语／实体标识 | 借鉴 Schema 引导与实体 grounding；生物医学词表不能直接搬入物流，名称匹配成功不证明关系成立 |
| LLM-Assisted Ontology Engineering and Construction of a French Legal Knowledge Graph，2026-07 预印本；HTML正文 [P3] | 先从样本发现语义结构，再按约束结构处理更大语料 | 采用“开放发现候选 Schema → 人工批准 → 封闭 Schema 抽取”。批准门是我们的工程补充，不是声称论文已实现企业审核 |
| AgentMap，2026-07 预印本；HTML正文 [P4] | 同时处理等价映射与上下位映射，利用检索和层次信息 | 类型等价、类型包含和实体同一性是三件事；向量相似不能直接生成 sameAs 或合并网点 |
| SciToolAgent-Evo，2026-07 预印本；HTML正文 [P5] | 研究本体感知的工具组织和持续工具获取 | 借鉴 ToolContract 的语义描述与经验反馈；不采用生产中自主安装、扩权或直接激活新工具的路径 |
| OLIVAW，2025；HTML正文与项目定位 [P6] | 将协作式本体开发与模型、数据、查询测试相结合，自动检查变更 | 把能力问题 CQ、Schema 差异、测试集和失败用例纳入 TE 发布流程；“查询能执行”还必须补“结果符合预期” |

以上近期工作中，有的仍是预印本。论文支持方法选择，不支持“可直接处理顺丰所有流程”“天然消灭幻觉”或“无需领域专家”的结论。技术评测还需复现实际模型、样本切分和工具版本。

### 2.1 由研究推导的构建方法

首先明确 Agent 必须回答的能力问题（Competency Questions，简称 CQ），再用跨文档类型、业务域和更新时间的分层样本提出 Schema 候选。Schema 经业务负责人确认后，抽取器只可使用批准的词汇与关系。遇到新类型或新规则，应返回扩展提案，而不是临时改 Schema 让输出通过。

将类型约束验证、证据蕴含判断、实体消歧、业务冲突和权限检查拆开。JSON 合法不意味着语义正确；节点存在不意味着边正确；多个文档重复同一错误也不意味着独立证据。每类错误分别形成 TE 问题单。

## 3. 开源工程横向选择

| 工程 | 可借用部分 | 不应假定的能力／采用方式 |
| --- | --- | --- |
| OpenViking [O1–O3] | Compile 任务与 Runtime 契约；现成 knowledge-graph Skill；上下文资产底座 | 图制品不是企业本体事务服务。作为主底座扩展，不把 relations() 的 URI 链接当事实主表 |
| teamEvolver [T1] | Runtime 外的进化控制面，候选、验证、回放与发布的产品方向 | 本轮仅 README 层确认；实际调用链、存储和权限需 PR00 核查。保留其唯一业务控制职责 |
| HugAgentOS [H1–H6] | Domain Pack、工具前置检查、分级审阅、版本与治理记录 | 不整体替换 TE／现有业务 Agent；CE、EE 与附加许可条款须单独审查 |
| OntoGPT [E1] | Schema 驱动的递归抽取、名称落地、未知名称保留 | 作为可替换抽取算子候选。物流实体目录、证据粒度、授权和提交仍由我们实现 |
| LinkML [E2] | 单一模型描述生成多种 Schema、代码和文档 | 作为设计期 Schema 编译工具；固定支持子集并测试生成物，不假定各目标语言语义完全相同 |
| RDFLib／pySHACL [E3] | RDF 互操作、SHACL 约束验证 | 离线或受限验证 Worker；验证不等于事实证明或权限授予，禁止不受控网络和任意脚本扩展 |
| DeepOnto [E4] | 本体操作、对齐、推理的研究工具链 | 更适合离线对齐实验；不将 JVM／训练依赖直接塞入 OV 在线热路径 |
| Graphiti [E5] | 增量与时间化知识图、证据关联；支持自定义／本体相关建模 | 借鉴时态与依赖设计，不增加第二套实时抽取和正式事实库；开源库与托管服务能力分开 |
| Microsoft GraphRAG [E6] | 基于图组织检索和综合信息的基线 | 保留为检索对照，不把检索增强框架当作动作权限、Schema 审批或本体发布协议 |
| IATA ONE Record [L1] | 航空货运的数据模型、语义与接口设计参考 | 仅对航空领域择取类与关系做映射；工作分支不等于已批准标准版本，也不代表顺丰已采用 |

不按星标排序：活跃度、提交数量和营销演示不足以说明跨租户隔离、源撤回、历史回滚和发布一致性已合格。复制代码前应固定 commit，并逐项检查 LICENSE、NOTICE、传递依赖和适用发行版；本表不是完整软件物料清单或法律审查。

## 4. HugAgentOS：值得借鉴，但不能直接视为成品底座

官方 Domain Pack 文档覆盖概念、关系、约束和工作流，具有草稿验证、发布版本及激活的设计；Ontology Harness 描述了确定性工具门禁、风险升级、审阅与人工修订链。[H2–H4] 最值得吸收的是把“模型理解语义”和“程序强制限制”分开，而不是每次工具调用都再请模型投票。

本方案据此选择三点：在 TE 中编辑版本化 Issue Pack；在 Agent 工具网关实施不可绕过的确定性检查；对高风险候选做独立审阅，失败记录回流 TE。但企业强制门禁不能由终端用户关闭，也不能依赖某个 Agent 主动选择是否加载 Skill。

同时保留三个边界。第一，官方架构说明把完整控制面描述为逐步集成的目标，不能把图中的所有模块当已验证实现。第二，社区与企业发行能力有边界，不假定团队权限、SSO 和完整审计全部可从社区包获得。第三，所查 LICENSE 在 Apache-2.0 基础上附加条件，涉及竞争性多租户 SaaS、归属展示及企业功能；内部单组织使用也应经过企业许可核对，而不是简单登记“纯 Apache-2.0”。[H1,H5,H6]

没有确认到可作为单独研究成果引用的 HugAgentOS 同名论文；本报告将其列为工程参考，不替它附会论文背书。读取深度为仓库说明、设计文档和许可文本，未运行其测试，也未完成所有门禁源码审计。

## 5. OpenViking 的具体复用切口

当前公开 main 的 `examples/compile/ov-compile-skills/knowledge-graph/SKILL.md` 已定义实体 Markdown 与关系 JSONL 制品，并要求类型、方向和逐条来源；重要多元关系可用中间节点表达。[O2] 因此不必从零再写一个“文档转图”的独立系统。

但该 Skill 的名称型文件 ID、来源 URI、重复边证据合并以及完整制品集提交，不能直接当成企业稳定 ID、不可变片段证据、独立证明逻辑或百万断言增量事务。我们的衔接方案是：旧制品先导入候选区；无法补齐证据版本或限定条件的条目隔离；正式迭代采用一次抽取输出结构化增量的 `sf-ontology-build.v1` Profile。人读图与 Markdown 从同一选中事实集合投影，不再重复抽取一遍。

v0.4.20 的公开 Compile API 文档可以确认任务接口和执行协议，但不证明用户部署已升级到该版本；main 的 Skill 也不能直接视为 v0.4.20 镜像内已安装内容。[O1,O3] 版本、Skill 制品格式、鉴权和取消语义均进入 PR00 的兼容性清单。

## 6. 标准使用边界

OWL 区分本体推理与数据库常见假设；缺少关系通常不能被解释为否定。[S1] 本方案用显式否定和 UNKNOWN 表达信息不完整，并只在源系统提供范围完整性证明时允许特定闭世界判断。SHACL 用于结构约束验证，不替代证据审核。[S2]

Palantir 的对象／链接／函数／动作思想可用于理解运行语义层，但不要求使用其商业平台。[S3] GS1 EPCIS 的对象、时间、地点、业务上下文和传感状态视角可用于物流事件；其中业务上下文的 “why” 不是事故根因证明。[L2] 航空部分可做 ONE Record 映射；全企业仍采用小型共享核心加业务模块，而不是把任何外部行业本体整包导入。
