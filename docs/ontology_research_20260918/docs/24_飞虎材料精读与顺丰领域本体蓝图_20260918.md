# 飞虎材料精读与顺丰领域本体蓝图

> 2026-09-18｜承接23号研究与25号V3方案。所有顺丰字段、接口名和示例规则均为设计提案，不是现网制度、系统代码或经业务确认的赔付口径。

## 1. 飞虎材料的精华与适用边界

来源是用户提供的《飞虎标志性技术：基于本体的知识蒸馏20260731.pdf》，共20页，已逐页阅读文本与页面图像。最后两页包含视频静帧，本轮没有视频或音频内容。

| 页码 | 材料表达 | 顺丰方案吸收／纠偏 |
| --- | --- | --- |
| 3—4 | 将知识表示、学习、应用分开；区分事实、程序与情节经验 | 用 Knowledge／Rule／Case 分开生命周期；认知架构类比不是已经验证的 Agent 能力定理 |
| 6、8—9 | Wiki 积累知识网络；业务本体承载对象、逻辑、动作边界 | Wiki 和 Ontology 共用来源及版本，不是两份各自更新的真相；语义服务与执行授权分别落实 |
| 11—12 | 诊断需要判断已有证据、缺失证据、工具和后续动作 | Issue Pack 必须包含必要证据、工具适用条件和不能下结论的情况，不只是相似问题到答案 |
| 13—14 | 从实际文档／工单逐步生长，围绕 Issue 组织局部网络 | 以小场景 CQ 驱动 Schema；抽取器产生候选，新增类型、冲突与高风险规则进入治理 |
| 15 | 诊断知识不接管真实业务数据实例 | 运单、扫描、航班、客户合同实时状态仍归源系统；OV 保存语义契约与受限证据引用 |
| 16—17 | 材料称已形成可运行 MVP；真实动作和生产状态闭环是下一阶段 | 可借鉴方法与示例，不能据此推断大规模生产有效性、错误率或硬门禁已经证明可靠 |

“知识蒸馏”在这里主要是把外部材料编译成可维护知识资产，**不自动等同于训练一个学生模型或将规则写入模型权重**。项目不应为了追求“内化”而删除原始证据、放弃实时查询或允许模型凭记忆执行业务动作。

## 2. 顺丰本体究竟要表达什么

建议将目标定义为：**让 Agent 知道业务对象是什么、证据说明到哪一步、还缺什么、哪些规则适用、下一步允许查询或提出什么，而不是让一个图数据库接管所有业务系统。**

形成三层语义、两种实例范围。

| 层／范围 | 示例 | 权威位置 |
| --- | --- | --- |
| 共享核心 Schema | 实体类型、关系、单位、适用条件、来源、时间 | OV，TE 批准版本 |
| 领域知识与诊断模型 | 产品定义、Issue、流程、状态解释、Rule、EvidenceSlot、ToolContract | OV 正式结构化资产；TE 管理构建和审核 |
| 场景包 Issue Pack | 签收争议所需证据、可用查询、冲突处理、转交条件、测试集 | OV 发布包；TE 负责领域配置与验收 |
| 稳定业务实体目录 | 网点、产品、服务区域的受控主数据引用 | 业务主数据系统为源权威；OV 保存版本化引用或批准的快照 |
| 运行态业务实例 | 某票件轨迹、某次扫描、某份客户合同的当前版本 | 源系统为权威；OV 只读受权证据句柄／短期快照，不能默认沉淀为共享知识 |

高频运单明细不应经过“实时事件 → LLM Wiki → LLM 再抽取图”链路。这样既可能迟滞，也会产生不必要的敏感信息复制和模型费用。历史案例只有经过脱敏、价值筛选、证据保留和审核，才可转为长期案例资产。

## 3. 保留既有14业务域，不把 Wiki 目录当本体类

同目录09号文件规定的四类 Page Role（TOPIC、REFERENCE、PROCEDURE、SYNTHESIS）、14个业务域、稳定 L2／L3、多视图和固定节点保护继续生效。下表是**建议的语义模块映射**，不是新增14套互相隔离的图。

| 既有业务域 | 建议核心语义／示例 | 模块协作边界 |
| --- | --- | --- |
| products | ServiceProduct、ServiceCommitment、EligibilityRule | 标准产品规则在此；具体客户报价不混入 |
| marketing | Segment、Campaign、Channel、MeasurementDefinition | 不把个人营销触达数据默认公开为知识 |
| sales | OpportunityType、QuotationRule、ContractHandover | 具体价格和客户条款依原权限；与标准产品区分 |
| customer-management | CustomerRef、CustomerTierDefinition、LifecycleRule | 客户实体优先权威ID，不以客户名称全局合并 |
| network-planning | NetworkNode、Lane、CapacityConstraint、DispatchPolicy | 计划与实际执行分开，不能从计划推断已发生 |
| operations | ShipmentRef、ParcelRef、LogisticsEvent、ProcessState | 收派、转运、分拣、空陆铁等共享事件和过程核心 |
| customer-service | ServiceIssue、TicketType、EvidenceSlot、HandoffRule | 首个只读诊断试点；客户陈述与系统事实分开 |
| quality-safety | ExceptionType、QualityMetric、CauseHypothesis | 异常相关性不是根因证明；生产安全规则高风险审核 |
| business-management | MetricDefinition、AnalysisMethod、DecisionRecord | 指标定义与一次经营结论分开，有效期分别管理 |
| enterprise-services | SupplierRef、AssetType、ProcurementProcess | 不替代采购／资产系统；审批动作由业务系统控制 |
| human-resource | RoleDefinition、LearningRequirement、HRPolicy | 不将员工个人属性及绩效通过本体扩大可见范围 |
| finance | SettlementConcept、CostMetric、CreditRule | 金额、币种、会计期间和合同适用范围不可省略 |
| technology | SystemRef、APIContract、ToolContract、ErrorMeaning | 系统状态码必须按系统与接口版本解释 |
| compliance | Policy、Obligation、DataUseRestriction、ApprovalRequirement | 管合法边界；业务 SOP 仍归其业务域，避免全塞合规 |

Page Role 是呈现用途，Domain 是业务分类，EntityType 是语义类型，Owner 是责任，ACL 是权限：五者不能相互代替。一个 Rule 可以由 REFERENCE 与 PROCEDURE 页共同支持，但仍只有一个稳定 Rule ID 和一套发布版本。Agent、部门、培训和客户项目通过视图与 Facet 引用，不制造复制的事实。

外部标准只做映射层：物流事件可参考 EPCIS；航空货运可参考 ONE Record；其具体版本、概念等价及字段映射必须经过领域核对。不能因为英文名称相同就设定 equivalentClass。

## 4. 最小共享元模型

| 类型 | 必备字段／约束 |
| --- | --- |
| EntityType／PropertyType／RelationType | 稳定ID、定义、domain/range、值类型、单位、适用限定、兼容版本 |
| BusinessEntityRef | tenant、实体类型、源系统、权威外部ID；名称仅是别名 |
| Concept | 术语定义、别名、适用业务域；与实例ID分开 |
| IssueDefinition | 症状／触发线索、必要对象、所需证据、允许诊断范围 |
| EvidenceSlot | 值类型、允许来源、完整性要求、时效策略、敏感级别；可为空但必须说明缺失 |
| Process／State／Transition | 过程版本、前后状态、触发证据、例外；计划状态与观察状态分离 |
| Rule／Constraint | 适用范围、前提、结论、优先关系、证据、解释模板、测试集 |
| ToolContract／BindingSpec | 工具版本、输入输出类型、字段解释、读写性质、源权限、超时和数据时效 |
| ActionType／ActionGate | 动作语义、条件、业务角色要求、风险、确认和幂等要求；不是执行许可本身 |
| TestCase | 输入证据、固定时点、预期结论／缺口／拒绝动作、来源分组、版本 |

每个可发布条目都必须有来源、有效期／适用时间说明和责任人。不能以模型置信分数代替这三项。

### 4.1 认识状态：避免把“说过”当“发生过”

`UserClaim` 是问题线索；`ToolObservation` 是受权查询获得的原始观察；`InterpretedSystemFact` 是按批准字段映射解释的系统记录；`DerivedFact` 是按固定规则从已验证事实推导的结果；`Hypothesis` 是待排查的可能原因；`Rule` 则是应如何判断的规范性知识。

例如，轨迹接口返回某条状态记录，只能先证明“该源系统在某时点返回了此状态”。要进一步判断“由本人签收”，需要相应字段和业务规则支持，不能把两者压成一个 delivered=true。客户说没收到，也不能单独证明系统错误或货物丢失。

## 5. 首个试点：签收争议／履约异常只读诊断

选择该场景是工程建议，不代表已经获得顺丰业务立项。试点只读现有证据，输出诊断摘要、缺口、下一步查询建议和工单草稿；**不自动改派、赔付、撤销签收或修改履约状态**。

最小实体可从 ShipmentRef、ParcelRef、ServiceProduct、NetworkNode、LogisticsEvent、ServiceTicket 开始；复用 Issue、EvidenceSlot、Rule、ToolContract 等共享类型。具体业务状态码、取证要求、可对外说明内容和责任岗位，须由源系统与业务负责人提供，不由本报告猜测。

### 5.1 能力问题 CQ 与验收回答

| CQ | 系统必须给出的结果 |
| --- | --- |
| CQ01：当前问题描述涉及什么对象？ | 实体候选及类型；不能把相似运单或同名网点合并 |
| CQ02：已有证据与客户陈述分别是什么？ | 分栏输出，标识来源、查询时点、证据等级 |
| CQ03：判断签收情况还缺什么？ | 必要 EvidenceSlot 列表，不凭空补值 |
| CQ04：哪个查询工具能取得该证据？ | 批准的 ToolContract 和必要参数；不暴露隐藏工具 |
| CQ05：接口状态具体意味着什么？ | 固定系统／接口版本的解释规则和原始证据引用 |
| CQ06：当前适用哪条产品／地区／客户规则？ | 规则版本、有效期、必要限定；无法确定则要求补信息 |
| CQ07：两个来源或新旧规则冲突怎么办？ | 展示有权限的冲突及分歧，阻止确定性结论 |
| CQ08：没有查到扫描记录能否推断未发生？ | 默认不能；只有范围完整性有保障的查询才能作特定否定判断 |
| CQ09：哪些下一步建议可以提出？ | 区分继续查询、补资料、转交和受限动作；不把建议当执行授权 |
| CQ10：更正或撤回来源后旧结论还可使用吗？ | 默认使用被阻断，依赖传播与重新编译状态可追踪 |
| CQ11：谁能批准这条规则？ | 当前有效的 accountable_owner／合格 reviewer，不能模型自批 |
| CQ12：为何未给出结论？ | 可理解的证据不足、时效不满足、冲突或权限原因，不泄露无权信息 |

试点可先建立上述12类 CQ 的多种正反例，再扩充真实场景；不能用模型自己生成并自己打分的案例集代替业务金标。业务测试集与提炼样本按来源家族和时间拆分，防止同一工单的不同改写同时进入训练式提示和验收。

### 5.2 一个纯合成的端到端例子

合成工单 `demo:ticket:001` 的用户陈述是“我没收到”；受信查询句柄指向 `demo:shipment:001` 的一条状态观察。诊断器先输出“用户陈述尚未收件；系统返回了一条签收状态记录”，而不是直接宣布“已本人签收”或“必须赔付”。

若缺乏足以解释签收方式的字段，返回 `missing_evidence=[receipt_method]`。若当前主体无权获取证明材料，返回可公开的证据不足提示，不返回材料标题或存在性细节。若规则版本或观察已过期，建议刷新；若新证据矛盾，进入待核查。任何受限业务动作仍交由独立业务网关检查，首版不执行。

## 6. Wiki 到本体的内容映射

TOPIC 提供概念和对象边界；REFERENCE 提供参数、术语和规则精确口径；PROCEDURE 提供过程、判断顺序和证据要求；SYNTHESIS 提供比较、复盘与假设。最后一种中的分析意见不能未经审核升格为普遍 Rule。

同一 Wiki revision 可支持多个语义候选；同一候选也可依赖多个来源。输入必须追到不可变 SourceRevision／Segment。原材料没有状态码定义、时效或动作权限时，抽取器应明确缺口。Wiki 的链接、目录、关键词共现和生成摘要都不单独构成事实证明。

新出现的 Issue、关系、流程步骤可进入 TE 的“Schema／Issue Pack 提案”；已批准 Schema 内的事实增量进入“断言候选”；索引与显示补链进入“机械投影任务”。三个通道不能混用，避免一次补链顺便改写业务事实。

## 7. 继承既有 Owner、审核和权限规则

以本轮实际回读的10号文档为准：双 Owner 是 **data_owner + accountable_owner**，不是擅自改成两个其他角色。非自然人 data_owner 必须关联可追责的人或岗位；独立 reviewer 不得与生产者合一。Wiki 运营负责人、Schema Steward 可以作为附加协作角色，不替代既有责任模型。

R0—R3 延用原语义：R0 为符合条件的权威源确定性映射；R1 为有完整证据的低风险抽取；R2 为跨源综合、操作方法和影响动作的结论，需人工审核；R3 涉及高风险内容、自动执行或 ACL 扩大，需领域与安全／合规复核。**它们不是模型置信度，也不是新的图节点等级。** 本方案另用只读、草稿、受控写、高影响描述运行时动作风险，避免同名混淆。

最终可用知识是已发布且有效资产、来源继承权限、当前用户权限、Agent 服务身份权限、Manager 使用范围和企业策略的交集。持有 View Scope 不等于拥有来源权限。来源撤回与权限收窄先在 OV 阻断，不能等 TE 夜间重编译才生效。

## 8. 业务输入缺口与后续验收

正式试点仍需业务方提供：权威状态口径与版本、真实字段字典、合法工具入口、源系统权限模型、证据时效要求、角色与转交规则、脱敏样本及金标。以上缺口不阻止先实现合同、存储、候选与查询骨架，但在缺口关闭前只能使用合成样本，不发布真实业务规则。
