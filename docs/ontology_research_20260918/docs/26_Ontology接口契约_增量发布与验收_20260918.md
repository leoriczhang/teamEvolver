# Ontology 接口契约、增量发布与验收册

> 2026-09-18｜配套25号V3。以下企业API、JSON Schema、SDK命名和服务状态均为新增协议提案。原生Compile接口单独标明；合成契约测试不是系统联调、授权审计或性能测试。

## 1. 三类契约不可混淆

| 类别 | 契约权威 | 本轮定位 |
| --- | --- | --- |
| 原生Compile／Task／Runtime | OV v0.4.20公开API文档 | 已查文档；部署兼容性待测，不修改其字段语义 |
| 企业知识构建／批准／本体查询 | 本方案新协议 | 需要TE／OV二开与共同验收 |
| 实际业务查询／写动作 | 企业IAM、源系统与工具网关 | 必须从真实接口登记，不虚构顺丰状态码或绕过既有审批 |

### 1.1 原生Compile需要保留的边界

原生创建入口是 `POST /api/v1/compile`，输入 `from` 目录数组、`to`、`skill` 以及可选 `instruction`、`args`，返回TaskRecord；任务状态通过 `/api/v1/tasks/{task_id}` 读取，取消通过对应 `/cancel` 接口。[O1]

部署选型时特别核对：内置Runtime对非空args的限制、外部Runtime认证材料传递、相同目标排队边界、用户重复提交与Runtime任务幂等的区别，以及取消不会回滚已写内容。具体行为以固定版本执行链为准；不能用原生任务completed替代语义审核成功。[O1,O3]

本方案在原生执行之前增加企业受理与凭证约束，在执行之后增加候选准备和合法提交。新增扩展字段不会不加转换地发送给原生Compile。

## 2. 构建接口

### 2.1 TE创建构建任务

`POST /te/enterprise/v1/jobs`，建议输入：

```json
{
  "profile": "sf-ontology-build.v1",
  "workspace_id": "customer-service-demo",
  "source_selection_ref": "selection-demo-001",
  "schema_revision": "sf-core@1.0.0",
  "issue_pack_revision": "receipt-dispute-demo@0.1.0",
  "mode": "delta",
  "budget_ref": "budget-demo-001"
}
```

来源选择、Schema与预算引用必须属于当前受信主体可用范围；tenant和最终执行权限由服务端解析。返回202与job_id，含状态而非“已完成”。TE生成冻结Manifest与base_generation后再调用OV企业受理。

### 2.2 OV企业幂等受理

`POST /api/v1/enterprise/compile-submissions`：

```json
{
  "submission_key": "job-demo-001:extract:1",
  "manifest_ref": "manifest-demo-001",
  "manifest_digest": "<64位sha256>",
  "profile": "sf-ontology-build.v1",
  "expected_generation": "gen-demo-000",
  "owner_epoch": 1
}
```

同键同规范化摘要返回原submission与ov_task_id；不同摘要409。正文中 `owner_epoch` 只是待比对的前提，当前值从OV注册表取。受理、原生任务登记和待派发事件必须按25号方案保持可恢复关联。

公开原生协议没有被本方案扩成“天生支持submission_key”。调用超时进入SUBMISSION_UNKNOWN；先按键对账，不重新发起未绑定的任务。候选计算可以在明确边界下至少一次，正式发布不能重复生效。

### 2.3 Candidate Bundle

建议传输使用Manifest加JSONL文件，存储接收端重算摘要。小样本与测试允许单JSON对象表示同一逻辑结构。

```text
manifest.json
schema_refs.json
entities.jsonl
assertions.jsonl
support_sets.jsonl
evidence.jsonl
rules.jsonl
issue_packs.json
bindings.json
tombstones.jsonl
validation_report.json
```

Manifest列每个文件的路径、类型、字节大小、行数和digest；路径必须归一化并限制在本任务staging，拒绝穿越、符号链接逃逸、超大行和重复制品覆盖。非必要的完整原文不重复放入每个bundle。

证据包含source_id、source_revision、segment_id、源摘要和准确定位。原生KG仅有URI时必须查回对应不可变版本；找不到则隔离，而不是绑定到“目前这个URI最新内容”。模型声明system_fact并不产生可信系统证据，必须验证受信连接器的证明。

### 2.4 Prepare与Commit

`POST /api/v1/enterprise/assets/prepare` 输入bundle引用、摘要、expected_heads／generation；输出prepared_id、已验证摘要、问题清单与可审核状态。不修改正式头。

`POST /api/v1/enterprise/assets/commits` 输入prepared_id、commit_key、PublicationGrant引用／签名；返回唯一receipt、generation、资产变更与投影水位。TE显示“已发布”必须依据receipt。

`GET /api/v1/enterprise/assets/commits/by-key` 用于响应丢失恢复。租户在认证边界确定，不能由调用者查询他人的commit_key。提交接口应区分重放已成功请求与不同内容复用旧键。

PublicationGrant至少绑定候选摘要、证据Manifest摘要、Schema／Issue Pack版本、基线、目标scope、批准记录、有效期及nonce。JSON Schema只校验字段形状；签名、当前权限、批准资格和一次性消费必须服务端实现。

## 3. Agent读取与诊断接口

### 3.1 Discover与Resolve

`GET /api/v1/enterprise/ontology/capabilities` 返回授权域内Schema／Issue Pack及支持的QueryPlan版本。这里的“支持”意味着服务真实具备，不是配置文件随意宣称。

`POST /api/v1/enterprise/ontology/resolve` 输入类型、别名或权威ID与scope。返回匹配方式 `authority_id / exact_alias / candidate`、多个候选与是否需要确认。相同名称不自动创建等价关系。搜索候选同样受权限保护，不能展示无权实体标签。

### 3.2 Typed Query

`POST /api/v1/enterprise/ontology/query`：

```json
{
  "contract": "sf.ontology.query.v1",
  "scope_ref": "scope-customer-service-demo",
  "schema_revision": "sf-core@1.0.0",
  "entity_ids": ["demo:issue:receipt-dispute"],
  "predicates": ["requires_evidence"],
  "valid_at": "2026-09-18T00:00:00Z",
  "known_at": "2026-09-18T00:00:00Z",
  "limits": {
    "max_hops": 2,
    "max_nodes": 100,
    "max_assertions": 200,
    "max_examined_edges": 5000
  }
}
```

以上数字是实验预算不是性能实测。服务端用角色和租户允许上限再收窄，不接受请求提升配额。执行计划仅允许批准类型、谓词、过滤和有界遍历；不接受SQL／SPARQL文本。缺少记录不是否定证据。

分页采用稳定键与签名cursor，绑定主体授权指纹、query摘要、generation与时点；翻页仍检查当前撤权。不能从隐藏节点扩展出可见邻居以泄漏其存在。

### 3.3 Context Compose

`POST /api/v1/enterprise/context/compose`：

```json
{
  "contract": "sf.ontology.context-request.v1",
  "scope_ref": "scope-customer-service-demo",
  "issue_pack_revision": "receipt-dispute-demo@0.1.0",
  "entity_refs": ["demo:shipment:001"],
  "claim": "客户陈述尚未收到，仅作为线索",
  "observation_handles": ["observation-demo-001"],
  "purpose": "read_only_diagnosis",
  "token_budget": 4000
}
```

ObservationHandle由受信网关生成，OV复核主体、任务、源版本、时效和权限；自由文本claim保持UserClaim。默认模型无权通过请求直接提交verified=true的系统事实。

响应为ContextPacket，至少区分：

```json
{
  "contract": "sf.ontology.context.v1",
  "schema_revision": "sf-core@1.0.0",
  "semantic_generation": "gen-demo-001",
  "facts": [],
  "missing_evidence": ["receipt_method"],
  "conflicts": [],
  "truncated": false,
  "degraded": false,
  "prompt_fragment": "尚缺少必要证据，不能确认本人收件；当前仅提供只读诊断。"
}
```

这是缩略响应例子；完整审计、权限水位、事实包和证据字段以附带ContextPacket Schema及25号语义为准。没有facts不意味着不存在事实，更不意味着所有候选原因均被排除。

### 3.4 Evaluate与Explain

`POST /api/v1/enterprise/ontology/evaluate` 接受Rule／Issue Pack版本和证据句柄。返回 truth=`true/false/unknown`，另有conflicts、missing、expired、used_rule_revisions。冲突不能被“取最新一条”掩盖。

`POST /api/v1/enterprise/ontology/explain` 接受调用者已获权的assertion／result引用，返回当前可展示的证明和裁剪状态。不返回任意内部隐藏节点，也不把推理过程里的模型草稿作为源证据。

可选 `/api/v1/enterprise/actions/preflight` 只评估语义前提，不产生真实执行授权。真实动作必须重新通过业务网关与源系统并取得回执；首版只读试点不开放自动执行。

### 3.5 Agent最小接入流程

Agent启动时发现自己有权的Issue Pack；收到任务后识别或Resolve实体；调用Compose取得必要规则与缺口；按批准ToolContract从业务网关取证；携带句柄再次Evaluate／Compose；形成受证据约束的解释或转交建议。

已有实体ID的结构化任务可跳过Resolve；本体查询和renderer不强制额外模型调用。反馈走独立 `ontology_feedback` 权限，保存候选问题而非修改正式事实。

## 4. 统一错误与状态

| 代码／状态 | 含义 | 调用端处理 |
| --- | --- | --- |
| 409 IDEMPOTENCY_CONFLICT | 同键不同内容 | 人工或调用逻辑修正，不重试覆盖 |
| 409 BASE_CHANGED | 发布基线改变 | 回TE重基准与必要重审 |
| 412 EVIDENCE_INVALID | 源撤回、摘要／证据不匹配 | 停止发布，影响分析 |
| 412 POLICY_CHANGED | 当前权限／Owner epoch变化 | 停止旧作业，重新冻结授权 |
| 422 SCHEMA_INVALID | 类型／限定／时间／关系不合法 | 形成候选问题，不自动改Schema |
| 429 BUDGET_EXCEEDED | 执行或查询配额耗尽 | 按Retry-After及父预算重排 |
| 503 AUTHORITY_UNAVAILABLE | 当前授权／源有效性无法确认 | fail closed；不使用旧缓存伪成功 |
| UNKNOWN／CONFLICT | 合法返回的知识状态，不是服务故障 | 补证据、刷新、缩小结论或转交 |

401／403／404及错误详情须按企业防枚举策略统一；隐藏内容的存在性不能经错误代码、计数或耗时差异轻易泄漏。表中细分原因首先供受权审计使用。

## 5. 增量状态机与关键竞态

每次source事件带source_id、source_revision、event_id、分区序列和来源高水位。消费者按event_id幂等；发现序列缺口补拉，不假设跨所有源全局顺序。

撤回到达时，OV先更新当前revocation／authorization epoch；所有查询与commit检查新水位。TE随后计算依赖闭包和修复Job。旧Runtime即使返回候选，owner_epoch、源有效性或base_generation不符也不得复活资产。

发布响应丢失时，以commit_key查receipt；投影失败只重试投影，不重跑模型；Schema升级期间保持明确generation，不把两个版本的规则混读；Source503标不可确认，不转成删除。业务写动作的检查与写入竞态由业务系统条件更新负责，不宣称OV检查一次就永久安全。

## 6. 机器可读交付与本地验证范围

本包包含：候选Bundle、ContextPacket、PublicationGrant和Typed Query的JSON Schema；合成样本；纯Python参考校验器与测试；API草案；原生Compile请求样例；验收矩阵。各文件标明draft，不会自动连接服务或发起真实业务操作。

参考校验器只检查选定子集：形状、引用闭合、证据必要性、明显来源性质不符、时间区间、限定、受限规则UNKNOWN传播、预算和纯函数可见性。它不验证真实源签名、不实现企业IAM、不做SQL事务、不调用LLM，也不证明部署中的权限隔离。

具体本地测试数量和结果以 `results/contract_test_results.json` 为准，JSON／YAML静态检查另记。下表系统测试无论本地纯函数是否通过，都仍为 `not_run`，须提供实际服务日志、数据库状态和审计回执后才能改为通过。

## 8. 实施交付与签收口径

P0交付固定源码／依赖／镜像／迁移版本证据；P1交付唯一发布与撤回；P2交付Wiki→候选→审核→正式本体的小范围纵切；P3交付Agent只读调用与CQ；P4交付增量、故障与规模化证据。没有实际服务回执的条目不得从not_run改成passed。

本地契约检查通过只说明样例和有限校验器在当前环境一致，不等于OV、TE或HugAgentOS已被测试。接入前应替换合成实体、scope、Owner、业务规则和源字段，固定真实工具／模型配置；不直接把demo内容发布进企业正式知识域。
