PROJECT ANATOMY / 工程解读

从个人经验，
到可验证的团队能力。

teamEvolver 把真实工作中的经验，转化为团队能持续复用的 Skill 与 Memory。理解这个项目，要同时看清：经验从哪里来、变化如何被验证、资产怎样可靠地交付给 Agent。

FastAPI + React本地对象存储 + OpenVikingSkill Evolution / Memory Evolution源码解读 · 非效果测评

01

先理解它解决什么

一个 Agent 把任务完成了，不等于整个团队都学会了这套方法。teamEvolver 要补上的，是从“一次做对”到“以后能稳定复用”的工程链路。

EXPERIENCE

经验可以追溯

保留 Session、工具使用、用户纠正与产物线索；把支持某项变化的事实提取为 Evidence，说明“为什么值得改”。

VALIDATION

改进可以验证

先生成 Skill Candidate，在真实 Agent 运行时执行同一任务的 Baseline 与 Candidate，再检查任务完成性和效率。

GOVERNANCE

能力可以治理

团队资产有版本、变更记录、分发状态与 Rollback 路径。个人资产与团队资产之间有共享边界。

一个贯穿全文的例子

假设团队经常让 Agent 生成月度经营报告。多次 Session 显示：Agent 总要等用户提醒，才补齐指标口径、异常解释和来源说明。这些重复纠正可以成为 Evidence，支持修订一项报告 Skill。系统再构造同类任务，验证加载 Candidate 后，Agent 是否能更少往返地交付完整报告。

TEAM SKILL / 怎么做

任务方法

例如：生成报告前先核对指标口径，按固定步骤定位异常，最后检查来源与解释是否齐全。Skill 包含适用场景、步骤、约束及配套资源。

TEAM MEMORY / 需要知道什么

长期上下文

例如：团队使用哪套指标定义，某业务线的统计口径为何调整。Memory 保存长期事实、背景或共识，供 Agent 检索使用。

项目定位：Agent 团队能力进化控制面业务任务仍由外部 Agent 运行时执行；teamEvolver 管理 Evidence、Evolution、验证、版本和分发。它内部也会调用 LLM、运行维护循环和验证分支，但不接管外部 Agent 的日常执行循环。

上面的经营报告场景为解释机制而构造，不代表仓库已经提供对应业务 Skill，也不代表已测得收益。

依据：[01] 定位与术语[02] 服务组装

02

工程架构：一个服务，三条进化链路

当前是模块化单体：一个 FastAPI 服务对外提供 API 和控制台，内部组合多个 Python 模块、后台循环与执行适配器。图中的模块不是独立部署的微服务。

边界负责什么理解这个边界的意义
外部 Agent ↔ 控制面Agent 上报 Session、读取 Context、执行 Replay Branch、接收 Skill Bundle。接入不是简单上传文本；能否验证，取决于运行时是否提供对应能力与材料。
React ↔ FastAPIReact + TypeScript + Vite 构建；FastAPI 挂载静态产物并提供管理 API。控制台是同一套后端能力的操作入口，不是另一个后台系统。
控制面 ↔ LLM摘要、Judge、候选规划、Dataset 合成、Checklist 判定、Memory 维护与文档挖掘。LLM 是多个阶段的依赖；一次 Evolution 的耗时和成本不等于一次模型调用。
本地存储 ↔ OpenViking默认本地承载服务账本与团队 Skill；OpenViking 承载 Context、Memory、快照和 Skill 镜像。OpenViking 不可用时，部分控制面路径仍能继续，但远端 Context 能力不会自动变成完整离线能力。

ProxyServer 通过多个 Mixin 组装路由；内嵌 EvolveServer 拥有自己的应用与周期循环，部分请求通过 httpx.ASGITransport 在进程内转发。因此，单端口背后仍存在多套状态与生命周期。

依据：[02] 服务组装[03] 前端与配置[14] 存储分层[10] Replay 运行边界

03

一份 Session，如何变成团队 Skill

这条链路的核心不是不断生成新内容，而是有依据地提出变化、验证变化，再把版本交付出去。不同阶段有分支、跳过和重试，不是每份 Session 都会走完全程。

Agent 使用后产生新 Session

  1. 接入：先确定是谁、使用过什么

    V1 Token 标识 Agent Integration；integration_id + external_subject 映射到 teamEvolver 用户。Session 可以携带完整交互、工具调用与结果、效率计数、Skill 使用和 Context 引用。受验证的 Context 使用信息比“某个 Skill 曾被注入”更有说服力。

    产出：规范化 Session 与可归属身份

  2. 过滤：决定是否进入 Skill Evolution

    主服务与 Langfuse 拉取复用 _ingest_session_dict。已处理且内容未变的 Session 可去重；增加新轮次则可重新处理。价值分类器输出 valuable、memory_candidate、task_only 或 chitchat。当前主路径只有 valuable 入队，其余归档并记录过滤审计。

    产出：持久化队列、归档、过滤审计、Session 索引

  3. 准备：先提取任务过程，再判断结果

    进化周期消费队列，生成 Session 摘要与执行轨迹，提取真实 Skill 引用，并按配置执行 Session Judge。Judge 会评价任务完成、响应质量、效率与工具使用。这是对来源 Session 的辅助评价，不是最终 Replay 发布分数。

    产出：摘要、轨迹、Skill 引用、Session Judge 结果

  4. 分组：按真实使用关联 Skill

    引用了 A 与 B 的 Session 会进入两个 Skill 分支；没有明确引用的 Session 进入无 Skill 分支，尝试提议新建。Skill 仅出现在注入目录中，不应被当作已使用。分支结合近期与历史 Evidence；默认要求至少 2 个不同 Session 和 2 个不同用户，受控候选审计 Session 有专门例外。

    产出：Skill 分组、规划用 Evidence、近期与历史验证窗口

  5. 规划：只让团队级任务经验改变团队 Skill

    LLM 规划修订、新建、描述优化、合并或 skip。Evidence Classification 位于候选规划规则中，区分 team_skill、user_memory、task_requirement、agent_runtime、insufficient_evidence。例如，一次报告要求“改成蓝色”不能直接升级为全团队方法。

    产出：变化理由、Evidence Classification、Skill 变化提议

  6. 物化：形成完整 Bundle，而不只改入口文字

    把允许的文件变更应用到原有 Bundle，计算多文件 Diff；保留未改文件，检查路径、类型和大小约束。候选通常包含 SKILL.md、引用资料与配套执行资源。新增或修改的 Python / Shell 资源进入静态语法检查；该检查不能证明业务正确或执行无副作用。

    产出：Skill Candidate、Bundle Tree Hash、静态检查结果

  7. 合成验证任务：用同源事实构建 Test Dataset

    Dataset Synthesizer 从支持变化的 Session / Evidence 构造任务和扁平 Checklist；近期窗口检验当前问题，历史窗口检验原有能力。默认合成参数包含 2 个测试任务、12–24 条要求、每批披露 4 条要求；这些是可配置默认值，不是每次运行一定满足的效果保证。

    产出：Replay Cases、Checklist、来源关联与验证窗口

  8. 验证：把 Candidate 放进真实执行过程

    服务端可调度候选评估，Validation Worker 也可在满足配置与空闲条件时收集结果。Baseline 与 Candidate 使用对应运行时执行任务，保存回复、工具轨迹、产物与效率。候选修改后会变化的 revision 和 Bundle Hash，用来防止旧结果为新内容背书。

    产出：版本匹配的验证结果、完成门禁与运行时兼容性结论

  9. 发布：根据实际配置选择门禁路径

    默认 publish_mode=validated，后台路径按验证结果数量、接受数量和运行时兼容性决定能否发布；管理员也可触发基于 Replay 的 Candidate Review。代码保留 direct 模式与管理员 force 路径，因此不能把“每次发布都必须人工点击、且指标更好”写成不可绕过的系统保证。

    产出：发布决策、新团队 Skill 版本、变更记录

  10. 交付与收尾：可重试，也要避免失败拖累整个周期

    发布进入统一 mutation 记录和持久化分发流程。成功处理的 Session 先归档再移出队列；失败分支涉及的 Session 留待重试。一份 Session 涉及多个 Skill 时，只要其中一个分支失败，它仍保留。之后 Agent 使用已交付版本产生新的 Session，才形成反馈闭环。

    产出：Agent 分发状态、Skill 镜像状态、可追溯历史
“11 阶段”适合展示概念，不能理解为 11 个必定顺序调用的函数。实际执行包括分组并发、无 Skill 分支、合并、候选合并更新、跳过、部分成功和异步验证。最可靠的入口是 EvolveServer._run_once → _evolve_skill_group / _handle_no_skill_sessions → _materialize_skill。

依据：[04] Session ingest[05] 进化编排[06] Evidence 与规划[07] Dataset[08] Candidate 治理

04

True Replay：先做完，再比较代价

一项 Skill 写得更像专家，并不能证明 Agent 用它做得更好。True Replay 让真实运行时执行任务，把判断落在行为与产物上。

BASELINE

不加载 Skill Candidate

同一 Replay Case 的对照分支。已有 Skill 的修订验证中可以加载当前已发布 Skill；新建 Skill 的场景可能没有对应 Skill。因此 Baseline 不能一概理解为“完全没有任何 Skill”。

CANDIDATE

加载待验证版本

对照相同任务，加载待验证 Bundle，并使用可复现的 Context 投影和必要材料。隔离执行目录与生产运行状态，收集分支实际交互、工具调用和输出。

渐进披露，检验能否主动完成

服务端持有 Checklist，每轮根据回复、工具轨迹和真实工作区产物判断完成情况。未满足的要求按批次继续披露，直到完成或耗尽轮次预算。更好的 Skill 有机会提前覆盖这些要求，减少用户补充和来回纠正。

例如，第一轮只提出“生成月报”，Checklist 检查报告是否解释异常、声明口径并列出来源。Candidate 主动完成这些内容，Baseline 经多次提醒才补齐，就会在交互轮次上拉开差异。这个差异来自任务执行，而不是给 Skill 文本打印象分。

当前源码中的精确决策规则

比较条件策略结论含义
Candidate 的非空 Checklist 未全部满足reject即使轮次和 Token 更少，也没有完成任务。
两边都有 Checklist，仅 Candidate 全部满足accept完成性优先于资源节省。
两边均完成；Candidate 轮次更少 / 更多accept / reject轮次优先，次级指标不能推翻这一步。
轮次相同；工具调用、Token 至少一项减少，且无一增加accept两个次级指标一起考虑，不是先工具数再 Token 的严格逐项排序。
轮次相同；工具调用或 Token 任一增加reject即便另一项减少，也不接受这种次级指标交换。

验证能力有三条重要边界

① Checklist 的满足情况仍可由 LLM 判定，具有误判可能；真实执行不等于评估完全客观。② 空 Checklist 在底层策略中可能退化为效率比较，不能当成完整完成性证明。③ 同源 Test Dataset 与候选来自相近 Evidence，有相关性偏差；还需要独立保留的任务、重复运行和人工抽查。

本地 Hermes 分支使用 Linux systemd-run、私有网络、只读路径和最小环境等约束，并通过模型 Broker 保留服务端密钥。外部 Agent 的 HTTP Replay 依赖其适配器和运行环境履约。当前代码不能支撑“在任何操作系统、任何 Agent 上都无需适配即可安全 True Replay”的结论。

05

团队 Memory：聚合与持续维护分工

Skill Evolution 关心可复用的方法；Memory Evolution 关心长期事实与背景能否保持准确、精简、可发现。当前代码提供两套互补机制。

DREAMCYCLE

维护已经积累的 Memory

通过计划、工具调用与持续检查，完成团队概况维护、去重、过期清理、个人经验团队化与新人可发现性检查。

主要入口：FullDreamCycleSupervisor → Scheduler → 各类 Job → ReActEngine。

CROSS-USER AGGREGATION

把多用户来源编译成团队资产

管理员选择用户与 Memory 类别，服务先制作确定性私有快照，再按固定版本的聚合 Skill 分层合并成团队 Memory。

主要入口：MemoryAggregationService，通过 OpenViking compile 完成语义编译。

DreamCycle 的真实执行过程

Supervisor 管理后台线程和轮次互斥；Scheduler 按配置的时间窗口和任务优先级执行。每个 Job 生成任务计划，ReActEngine 在“查看状态 → 调用模型 → 执行工具 → 更新计划”的循环中工作，受轮次预算与连续错误上限约束。

工具侧提供搜索、读取、浏览、写入、归档与合并；写入前强调先查重、优先更新已有权威条目，临时诊断报告保存为报告而非长期 Memory。部分完成判断锚定成功的写操作，减少“模型说已维护，实际上没改动”的问题。

跨用户聚合：先准确复制，再分层处理

步骤具体实现为什么这样做
固定聚合规则读取可修改的聚合 Skill，计算内容指纹并固定本次运行 revision。一次聚合中不应因中途修改规则而产生前后不一致。
生成确定性快照逐用户制作 JSONL，保留来源 URI、相对路径、内容、修改时间和 SHA-256；这一阶段不调用模型。将来源采集与语义变换分离，便于追溯，也能按指纹复用。
有界 tree-reduce先分组合并，再逐层合并中间结果；限制 fan-in 和 compile 并发。避免一次把全部用户 Memory 塞进上下文；但分层压缩仍可能损失细节。
保留团队已有内容按配置把当前目标树做成 baseline 输入，要求保留只存在于团队树中的人工修订。避免重新聚合把团队既有结论覆盖掉；仍需关注编译结果是否遵守约束。
增量与恢复保存用户来源、Skill 指纹与合并状态；来源不变时复用快照；规则变化触发重新编译。还提供可选的增量发布路径。减少重复模型成本，失败重跑可复用成功工作。不是全账户多文件事务。

默认聚合 Skill 要求去个人化、合并同主题内容、记录来源、维护 Markdown 索引与交叉引用。输出含 entity、concept、synthesis、index 等类型。注意：正文去个人化与来源元数据保留是两件事；包含用户标识的 provenance 仍需访问控制。

“挖掘成功”与“可发布”不同

生成唯一可识别的 SKILL.md 后，挖掘任务可能带 warning 完成；提交 Skill Candidate 前仍要补齐所需评测材料。文档产出的内部 Benchmark 也不能直接充当已完成 True Replay 的证明。

还提供两条评测旁路

轨迹 Benchmark 挖掘可直接从交互轨迹构造独立评测产物；LIFT 桥接把评测材料转成可检查、批准和发布的外部格式。这些路径有独立用途，不能混同于主 Skill Evolution 发布链路。

适合补齐冷启动，不能替代领域专家。文档本身可能过期、冲突或缺少执行细节。语义发现与反思环能把缺口显式化，但不会自动证明提取的方法有效；生成的 Skill 和评测定义仍需要领域校验与真实任务验证。

08

存储与一致性：发布成功，不等于所有 Agent 已更新

存储设计决定系统在故障、重启和并发时能否继续工作。当前默认将高频服务账本留在本地，并把远端 Context 能力与异步交付分开。

对象默认主位置 / 机制作用与恢复边界
Session 队列、归档、索引、过滤审计本地对象存储；sessions/、session_archive/、session_index.json 等。队列可继续消费，归档支撑追溯。队列删除不应先于归档完成。
Evidence、Candidate、验证结果与 registry / manifest默认本地账本 / 对象存储，经对应 Store 管理。帮助解释候选来源、识别版本、保存决策；不是远端向量检索的高频写路径。
团队 Skill 与历史 Bundle本地先提交，Skill 子树通过 spool 异步镜像到 OpenViking。正文、资源、版本与 Hash 需要一致；manifest / registry 不属于该 Skill 子树镜像。
Agent 分发skill_sync_outbox/、commit 与 tombstone；适配器送达。有 pending / 重试 / delivery 状态。中心版本成功不意味着远端立即全部收到。
Memory、Resources、SnapshotOpenViking Context 接口与快照能力。依赖外部服务、身份与相应 API 支持；本地 fallback 无法替代全部远端能力。
配置、认证及运行状态主要位于 ~/.teamEvolver/；部分目录可配置。正式部署需持久卷与备份；不能只备份 OpenViking 就认为状态完整。

一次 Publish 的三条状态线

1. 中心版本

写入 Bundle 与版本信息，形成 mutation commit；这回答“团队当前决定使用哪个版本”。

2. Agent 分发

durable outbox 通过适配器发送版本与 Hash，并记录各目标结果；失败后可重试。这回答“哪些 Agent 已拿到该版本”。

3. Context 镜像

独立 Skill mirror spool 将需要的 Skill 子树写入 OpenViking；镜像失败不应阻塞本地进化。这回答“通过远端 Context 读取时能看到哪个版本”。

Rollback 是“用历史内容生成新版本”

若 v8 有问题，要恢复 v5 的完整 Bundle，Rollback 应产生一个新的 v9，内容对应 v5；旧版本与审计链保留。Delete 则产生带版本信息的 tombstone，让分发端知道应删除，避免历史内容因重试再次出现。

两种“本地”不要混为一谈。默认本地为主的 Skill 库有明确异步镜像；OpenViking 不可用时临时启用的通用 LocalObjectStore fallback，代码明确说明没有通用自动回写远端。恢复远端服务不会自动合并所有回退期间的写入，也不代表现有 Store 实例会立即重新绑定远端。

LocalObjectStore 用锁、临时文件与 os.replace 降低单文件写入撕裂风险，回退目录按存储身份区分。但单文件原子替换不等于跨 Bundle、manifest、commit、outbox 的多对象原子事务，也不等于多进程分布式锁。

依据：[14] 本地 / 远端存储[15] mutation 与镜像[04] Session 账本

09

创新点与工程长处

这里的“创新”指项目在能力进化流程上的组合设计与工程特点。仅凭仓库分析，不能证明其学术首创、行业领先或效果优于其他产品。

01 / EVIDENCE-DRIVEN CHANGE

把“值得改”与“可以共享”分开判断

结合真实 Skill 使用、用户纠正、Evidence Classification 与跨用户最低要求，尽量避免把个人偏好、一次性任务要求或 Runtime 故障固化为团队方法。

价值：减少无依据的团队资产变化。
边界：分类仍受模型判断和来源完整性影响。

02 / EXECUTION-BASED VALIDATION

通过渐进披露验证主动完成能力

让 Baseline / Candidate 在真实工具循环中执行任务，Checklist 控制完成性，轮次体现用户需要补充多少要求。

价值：比单纯评阅 Skill 文本更接近实际使用。
边界：任务与 Checklist 的质量直接影响可信度。

03 / HISTORICAL EVIDENCE

让变化记住之前的事实与失败

Evidence 跨周期保留，近期与历史窗口同时参与规划和验证；Candidate revision / Bundle Hash 约束结果适用范围。

价值：减少只修当前问题、忘掉历史能力，以及用旧结果发布新内容。
边界：有限窗口仍无法覆盖全部历史场景。

04 / FULL-BUNDLE GOVERNANCE

把可执行资产作为完整 Bundle 治理

变化不仅覆盖入口内容，还涉及引用资源、多文件 Diff、静态检查、完整版本恢复、删除传播与交付追踪。

价值：更适合包含执行资源的 Skill。
边界：最终一致性与修复机制仍需故障验证。

05 / INCREMENTAL MEMORY

确定性采集与语义聚合分层

先按指纹复制来源，再固定聚合规则做有界 tree-reduce；中间状态可复用，目标已有内容可以作为合并输入。

价值：为多用户 Memory 聚合提供成本与追溯控制。
边界：分层摘要、去个人化与保留人工修订仍存在语义误差。

06 / WHITE-BOX OPERATIONS

把进化过程变成可检查的工程过程

控制台暴露过程参数、Prompt、Evidence、Diff、验证轨迹、分发状态与 Lab；Langfuse 提供跨阶段观测入口。

价值：管理员能定位“为什么生成、为什么通过、为什么没送达”。
边界：配置自由度也会增加复现与治理难度。

依据：[05] 编排[06] Evidence[09] 判定[13] 聚合[15] 版本交付[18] 观测

适用场景：重复任务多、反馈可观察、改进可验证

以下是基于架构的适配性判断，而非客户案例或已验证收益。判断是否值得接入，先看是否存在可持续积累的团队任务经验。

场景最有价值的能力适配判断与前提
研发、报告、分析等重复交付Session → Skill Evolution → True Replay较适合任务可重做、产物可检查，重复纠正能反映方法缺陷。需要稳定执行环境和测试材料。
客服、运营等领域流程沉淀SkillMiner + 后续真实 Session 反馈较适合已有可靠领域资料，且能把边界条件转为可验证任务。需要专家核查规则与结果。
多用户长期协作与新人上手跨用户聚合 + DreamCycle + Context Workspace较适合团队事实分散、重复、过时，且有明确共享范围与负责人。
多种 Agent 统一管理团队能力Agent Protocol V1 + Bundle 分发 + 运行时兼容性有条件适合各 Runtime 需要提供真实的 ingest、Context、Replay 与 Sync 能力；声明兼容不能替代运行验证。
只有一次性任务，或来源极少可用 Lab / 文档挖掘做探索完整平台收益有限重复任务和多用户 Evidence 不足，难形成持续 Evolution 闭环。
必须访问生产外部系统的不可重现任务需额外执行环境与副作用控制接入成本高例如真实交易或不可逆外部操作；若缺少可隔离环境，就不能获得可信的对照执行。
强一致、多副本高可用或大规模多租户平台当前可作控制面原型基础需要补强本地账本、进程内锁、对象级提交和 Runtime 依赖都需要进一步系统化治理。

一条可落地的试点路线

  1. 选一个有重复纠正的真实任务。先接入一个 Runtime，确认 Session、工具结果、产物与身份映射可靠。
  2. 先建立可验证的输入。确定团队允许共享的 Evidence，整理可重现的任务和独立保留的评估任务。
  3. 观察少量 Candidate 的完整生命周期。逐项看变化理由、Bundle Diff、Checklist 和真实轨迹，再检查 Agent 实际收到的版本。
  4. 验证收益和成本，再扩大范围。对相同任务做重复运行，记录完成率、往返次数、工具调用、Token、实际耗时、验证成本与人工时间。
  5. 补齐恢复路径后，再启用持续维护。试验队列重启恢复、分发重试、Rollback、镜像故障；随后逐步加入团队 Memory 聚合与 DreamCycle。
如何判断试点有收益不要只看生成了多少 Skill。可以估算：重复任务次数 × 每次节省的人工 / 执行成本 − Evolution、Replay 与维护成本。最终还要确认任务完成质量没有变差。仓库未提供本次环境的实测收益，本文不填入任何虚构百分比。

不足：把设计约束与现状区分开

项目的能力面已经较完整，但“代码有这项机制”不等于“任何配置都能保证成立”。以下区分直接读到的实现事实、由架构推导的风险，以及后续改进建议。

先说明代码与总览叙述的差异

常见理解当前源码支持的更精确说法
Session 分类后会自动路由到 Skill 或 Memory主 ingest 路径只把 valuable 入队；memory_candidate 等直接归档。Memory 聚合有独立来源与入口。
效率按轮次、工具调用、Token 严格依次排序轮次优先；轮次相同时，工具与 Token 至少一项变好，且两者都不能变差。
每个团队 Skill 版本必经人工门禁存在自动验证发布、管理员 Replay 发布，以及 direct / force 分支。治理效果受配置与路径影响。
Memory Change 必先 Replay 再应用目前包括已应用变化的前后验证与未保存内容验证，不是统一写前强制流程。
所有变化都由一个事务原子完成Bundle、索引、commit、outbox 等是分开的存储操作，以记录、重试和 reconcile 提升可恢复性。
OpenViking 回退期间写入会自动回到远端通用本地 fallback 没有自动 sync-back；有单独镜像能力的是团队 Skill 子树。

影响工程成熟度的主要问题

问题与证据类型具体事实 / 风险改进方向
全局 LLM 并发边界
代码事实		AsyncLLMClient.chat 使用 asyncio.to_thread；进化分组有局部 Semaphore，但该客户端没有工程指引要求的专用执行池 + 全局 ≤8 Semaphore。DreamCycle 等还存在独立模型调用路径。统一模型调用预算与限流域，把摘要、规划、Replay 判定、Memory 维护纳入总体资源上限。
Session 索引写入
代码事实		_merge_session_index 在进程内锁下整体读取、合并、写回，保留最多 10,000 条索引项；尚非指引所说的合并队列 + 周期 flush 单写者实现。归档并非因此只保留 10,000 份。落实单写者 / 事务型索引，给高频 ingest 提供明确背压；设计多进程访问和更长历史的查询策略。
异步路由与同步存储
代码事实		主 _ingest_session_dict 直接调用 SessionStore 同步方法；默认本地写入仍占用事件循环，显式切换远端后影响更明显。高频本地存储也是可配置默认，非所有 override 都被硬禁止。按调用边界隔离同步 I/O；对违反高频存储分层的配置给出明确校验。
多对象一致性与扩展
架构推断		多处进程内锁和 JSON 账本适合单实例运行，但不能直接推导多副本安全。中心提交、分发和镜像之间存在短暂差异。扩大部署前定义唯一写入者、幂等键、事务边界和失败恢复协议，并做故障注入验证。
验证成本与统计可信度
架构推断		每个 Case 至少执行两条分支，再加 Dataset 合成和多轮判定。默认少量同源任务可能对特定 Evidence 过拟合，单次效率差异也可能来自模型随机性。保留独立任务，重复运行，报告分布与不确定性；把真实耗时与经济成本作为补充观察。
Memory 治理闭环
代码事实		Memory Change 的风险字段仍可为 unclassified，Memory Replay 可发生在应用后；快照失败会减少可验证性。去个人化主要由聚合规则指导。定义风险分级、需要人工处理的变化、快照缺失策略与可验证的共享检查。
运行时与平台依赖
代码事实		本地 Hermes Replay 需要 Linux systemd 隔离设施；外部 Replay 需要适配器提供真实执行、Context 与指标。安装 FastAPI 成功并不能证明 Replay 可用。给不同 Runtime 建立能力矩阵、隔离自检和端到端接入用例。
大型编排模块与文档漂移
代码事实		当前 orchestrator.py 4,806 行，routes.py 5,158 行；多个模块和文档同时描述发布、验证与状态，容易产生不一致。按生命周期拆分编排职责；从策略与契约生成说明，持续校验文档和默认配置。

术语速查

以下解释遵循项目 CONTEXT.md；这些概念分别对应不同阶段，不能互相替换。

Session
一次围绕任务产生的完整交互记录，包括工具调用、产物、Context 使用与效率。
Evidence
从 Session、领域资料或历史资产中提取，能支持某项资产变化的可追溯事实。
Evidence Classification
判断事实应该影响团队 Skill、个人 Memory，还是只属于当前任务、Runtime 问题或不足以支持变化。
Skill
可执行、可复用的任务方法，明确适用场景、步骤、约束和配套资源。
Memory
可检索的长期事实、背景、偏好或团队共识，不直接规定完整任务流程。
Skill Candidate
基于 Evidence 提议的新建或修订版本，验证与发布前不改变已发布团队 Skill。
Memory Change
对团队 Memory 的新增、合并、修订、去重或归档提议；当前代码也用它记录已执行变化。
Test Dataset
与 Skill Candidate 同源生成的任务集合，用于对比真实执行。本文将其与 SkillMiner 的内部评测产物分开描述。
Checklist
单个 Replay Case 必须满足的扁平完成条件集合；是完成门禁，不参与加权效果评分。
Baseline
不加载 Skill Candidate 时执行同一 Replay Case 的对照分支，可能保留当前已发布 Skill。
True Replay
在隔离的真实运行时中执行 Baseline 与 Candidate，按渐进披露协议检验完成性与效率。
Candidate Review
管理员基于 Evidence、静态检查和 True Replay 结果决定是否 Publish 的门禁。
Publish / Rollback
前者固化新的团队 Skill 版本并分发；后者以新版本恢复历史完整内容，保留版本与审计链。
Agent Integration
一个外部 Agent 运行时在 teamEvolver 注册的身份、能力声明与受控访问边界。
个人资产 / 团队资产
个人资产归属单个用户；团队资产经过共享性判断与团队治理，授权成员和 Agent 才能使用。
DreamCycle
持续执行团队 Memory 聚合、去重、清理、概况与可发现性维护的进化过程。
