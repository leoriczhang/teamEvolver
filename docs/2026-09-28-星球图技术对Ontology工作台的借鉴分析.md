## 结论摘要

分享文档本身讲的是三维可视化实现，对构建侧价值有限；但**线上版背后的一份"快件质量业务本体快照"暴露了另一套本体构建方法论**，其中四件事对本项目有直接参考价值：

1. **属性级的 authority × completeness 双维度量化**——他们能回答"这套本体 516 个属性里 327 个完备、52 个部分、11 个桩、126 个未设"，我们的审核面对 ≤10000 条断言没有任何分诊依据（`team_miner` 已有"置信档"先例可对齐）；
2. **Schema 提案的 dataTypeBasis**（observed / named / default）——类型是"观察出来的"还是"兜底默认的"必须显式标注；
3. **使用驱动的本体演化闭环**——他们从 LLM 会话日志挖掘任务类型（"9 天 3239 轮，抽 30 条归纳"），提案自带归纳证据；我们只从文档构建，反馈仅进运营评审；
4. **分享中的"状态贴图"工程哲学**（只改几十字节、不动几万粒子）——对应我们一直没落地的增量编译（manifest `mode: delta` 字段存在但 rebase 仍全量重编）。

另有快照导出、上下文分层两项中价值借鉴，见第四节。以下逐项展开。

## 一、材料与关键发现

### 1.1 分享文档：可视化实现（构建侧价值有限）

幻灯片 8 节（Demo / 代码结构 / 节点布局 / 颜色 / 发光 / 粒子 / 连线 / 标签与相机）全部围绕 three.js 渲染展开。与构建相关的只有三条工程原则，且属于"印证"而非"新增"：

- **确定性**：布局完全由数据决定、可复现——与我们 `candidate_from_drafts` 的确定性后处理（[compile_contract.py:175](../team_ontology/compile_contract.py#L175)）同构；
- **极简封闭契约**：`STAR_DATA = { center, nodes, links, hotPath }`，每个字段单一语义，"换数据只改这一段"；
- **状态贴图**：把不可变的大块数据（几何）与可变的小块状态（亮度）分离，交互只更新状态——**这是对构建侧最有启发的一条**，见第四节 D。

### 1.2 关键发现：线上版是"业务本体快照"（构建方法论的直接样本）

幻灯片中嵌入的线上页 URL 为 `/ontology-view/`，其 `data.js`（150KB，已拉取分析）自述：

> "本体快照。取自快件质量业务本体，导出时间见下方 capturedAt。这一页是离线展示版：所有数据都在这个文件里，页面不向任何服务发请求。"

> "严格说某一次执行不是本体——本体只装不随状态变的东西，所以第三层叫执行实例，不叫应用本体。"

## 三、构建侧借鉴建议（按优先级排序）

### A. 属性/断言级 completeness 量化——审核分诊与健康度（★★★★★，成本中）

**他们的做法**：516 属性中 full 327 / partial 52 / stub 11 / unset 126，一眼看清本体"哪里虚"。发布前可以量化质量门槛。

**我们的现状**：候选最多 10000 断言 + 10000 实体（[wire.py:140-141](../team_ontology/wire.py#L140-L141)），审核页平铺全部事实；35 号验收文档明示"人工审核成本"是未解痛点。reviewer 没有优先级依据。

**落地**：
- `Assertion`（或评审产物层）增加 `completeness` 维度，初值由 `candidate_from_drafts` 确定性计算：有完整 support_sets → `full`；多源不一致 / 证据单薄 → `partial`；仅提名无证据 → `stub`；
- 评审页按 completeness 排序分诊（stub 先审）；发布版本页展示每代的分布统计；
- 发布门槛可量化（如 stub 占比超阈值时警示）。

**内部先例**：`team_miner` 的 Skill 编译已输出"置信档与待补缺口清单"（[team_miner/README.md](../team_miner/README.md) 第 3 条）——本体侧对齐后，两个模块的质量语言一致。

### B. Schema 提案的 dataTypeBasis（★★★★☆，成本低）

**他们的做法**：每个属性的类型标注得出处——`named`（来源明示）/ `observed`（数据观察）/ `named+observed`（双证）/ `default`（兜底）。他们的数据里 default 占 116/516——**兜底默认值被显式暴露而不是藏起来**。

**我们的现状**：`schema_basis` 只给证据定位，reviewer 无法区分"这个 value_type 是 30 个草稿都这么写"还是"编译器兜底默认"。

**落地**：schema 提案的 `entity_types` / `predicates.value_type` 附带 basis（observed + 出现次数 / named + 出处 / default），在 schema_review 阶段（[OntologyView.tsx:96](../web-ui/src/views/OntologyView.tsx#L96)）随证据定位一起展示；`default` 项默认标黄提请人工确认。

### C. 使用驱动的本体演化闭环（★★★★☆，成本高，战略项）

**他们的做法**：任务类型不是拍脑袋写的，是从 9 天 3239 轮 LLM 会话里抽 30 条归纳的，`status: "inferred"` + `basis` 全程留痕，`touches` 把任务映射回本体类型。

**我们的现状**：本体只从文档构建（冻结来源 → Compile）。"使用反馈"页的反馈只进 OV 运营评审；35 号验收文档列出的"检索增强仅按别名展开、完整概念关系扩展未做"等缺口，根源之一就是缺少使用信号回流。

**落地**（基础设施大部分已存在）：
- `session_ingestion/`（会话摄取）+ `team_miner` 的轨迹挖掘（README 第 6 条：已支持 teamEvolver/SkillGen/OpenAI messages 风格轨迹）→ 挖掘高频查询模式与反复出现的未建模概念；
- 产出 `schema_proposals`（V5 engine 遗留通道正好是着陆点），每条提案必须携带归纳证据（轮数 / 采样数 / 代表会话引用），走既有 `schema_review` 人工确认——**证据纪律与现有流程同构**，不是绕开人工。

### D. 增量编译——"状态贴图"哲学落地（★★★★☆，成本高，治本项）

**分享的做法**：粒子几何（几万个点、不可变）与状态贴图（每节点 1 像素、可变）分离，"点一个球时只改这几十个字节，不用动几万个粒子"。

**我们的现状**：`mode: delta` 字段在契约里躺了很久（[wire.py:87](../team_ontology/wire.py#L87)）但从未真正实现增量——rebase 全量重冻结、重编译。后果链：SIT 实测单任务 26.3 分钟 → 固定 30 分钟超时失败 → 被迫做自适应墙钟 spec（`docs/superpowers/specs/2026-09-28-adaptive-compile-deadline-design.md`，已批准未实现）。**自适应墙钟是在给症状打补丁，增量编译才是病因治疗**。

**落地**：
- 来源冻结时已带 revision/digest——变更检测免费可得；
- 重编译时只对变更来源重跑 Compile 批次，未变更来源复用上一代候选断言（按 source_id 对齐 + digest 校验）；
- 撤回（source-events）天然受益：撤回一个来源 → 只 tombstone 依赖它的断言，其余不动——这正是"跨来源自动依赖修复未实现"的已知缺口（35 号验收文档）。

### E. 生成快照导出 + 健康统计（★★★☆☆，成本低）

**他们的做法**：整份本体导出为版本化、离线自包含的快照（`version` + `capturedAt` + `stats` 汇总 + 完整图），双击即看、不发请求。

**我们的落地**：新增 generation 级快照导出（或增强 `/jobs/{id}/export`）：`stats`（类型/谓词/authority/completeness 分布）+ nodes/links 按文档化契约输出。用途：审核结果离线分发（缓解人工审核成本）、审计归档、给未来任何可视化一个稳定数据契约。

### F. ContextRequest 增加分层（★★★☆☆，成本中）

**他们的做法**：`?zoom=domain/task/instance` 三层（Guarino 分层）；领域层"只装不随状态变的东西"，因此稳定、可缓存。

**我们的落地**：`ContextRequest` 增加 `level` 参数——`domain`（Schema 摘要：类型 + 谓词 + 关系骨架，按 schema_revision 缓存复用）/ `instance`（现状：实体 + 断言）/ `task`（工作流视图）。当前 4000 token 预算只装得下实例层；领域层一次请求、多会话复用，直接服务"完整概念关系扩展"的检索缺口。

### G. Schema rules 带 basis + status（★★☆☆☆，成本低）

constraints 的模式值得抄：`basis`（"⚠️ 从字段名推断，待业务确认"）+ `severity` + `status`。我们的 `rules[]`（[wire.py:49-54](../team_ontology/wire.py#L49-L54)）目前无出处无状态——补两个字段，评审页即可展示"这条规则是推断的还是确认的"。

## 四、构建侧不建议照搬的部分

| 不照搬 | 理由 |
|---|---|
| 标注式溯源替代校验式溯源 | 快照的 `basis`/`meta` 是人工/脚本标注的说明文字；我们的证据校验是流水线强制的（quote 精确子串 + 位置唯一性）。借鉴元数据维度时校验标准不放松 |
| policies / visibility（ABAC 挂本体） | 短期用不上：OV 授权已是账户级且够用；等出现"敏感谓词按角色可见"的真实需求再做，避免 Schema 提前复杂化 |
| 执行痕迹进本体 | 对方自己也明确"某一次执行不是本体"——hotPath 是叠加层。对应我们：动态执行上下文留在 ContextPacket 组装层，不固化进 Schema |
| metrics 体系（58 个带方向的指标） | 运营指标工程，与本体构建正交；等本体稳定后作为消费方接入，不作为构建目标 |

## 附录 A：前端可视化借鉴（v1 内容，按反馈降级保留）

**现状**：工作台全部图可视化是 [OntologyView.tsx:28-40](../web-ui/src/views/OntologyView.tsx#L28-L40) 的 13 行内联 SVG——固定网格（每行 4 个）、硬截断前 30 实体、零交互、predicate 标签放线段中点必重叠；两处使用：候选实体图（[:110](../web-ui/src/views/OntologyView.tsx#L110)）与领域包图（[:114](../web-ui/src/views/OntologyView.tsx#L114)）；compare 差异以原始 JSON 输出（[:120](../web-ui/src/views/OntologyView.tsx#L120)）。

**值得抄的思想**（2D SVG 实现，不引 three.js）：
1. **确定性同心圈布局**：entity_type 分圈、断言度数作权重（**圈内归一化**，不跨圈比大小）、圈半径按标签数自适应、相位错开——评审要求同一候选两次渲染逐像素一致；
2. **聚焦交互**：点实体 → 邻域高亮 + 其余压暗 + 断言列表滚动定位 + Esc 复原；拖动/点击以 4px 位移判定；
3. **状态高亮语义**：评审决策三色（approved 绿 / rejected 红 / 待评审灰，数据已在 `extraction.reviews`）；compare 差异三色（added / removed / changed）替换 JSON dump；
4. **标签碰撞避让**：屏幕矩形两两比较 + 推开/回退（算法照搬 star.js:386-401）。

**不照搬**：3D / 粒子 / 泛光 / 深色主题 / 自动旋转 / 入场动画——工具界面要精确可读；three.bundle 719KB 与轻量 SPA 不成比例。但若做对外演示资产，`star-demo/` 换 data.js 可直接复用。

**规模约束**：圈布局舒适区约 30–300 节点；契约上限 10000 实体必须配类型聚合折叠 + 筛选。线上快照本体 66 节点也在舒适区内。
