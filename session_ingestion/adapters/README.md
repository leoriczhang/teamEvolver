# Tenant Data Source Adapters

Each top-level `.py` file in this directory is a bundled data source Adapter template. An Adapter connects to an upstream (Doris, Langfuse and others), filters records and converts them into standard Sessions; the platform only consumes standard Sessions. Start with `example-doris.py`, `example-langfuse.py`, `example-shared-langfuse.py` or `example-custom-mapping.py`. These examples are disabled until configured.

A file declares a literal `SOURCE` dictionary and a top-level `build_adapter()` returning an object with `health`, `list_session_ids`, `iter_session_id_batches`, `fetch_session`, `convert_session` and `close`. `SOURCE.supported_filters` and `required_filters` drive the console form; `SOURCE.max_sessions` is only the preview default and never limits a pull. Credentials come from environment variables, never source literals. Validation rules are in `_runtime.py:validate_content`.

Adapter source is versioned in PostgreSQL (`adapter_versions`) and bound per tenant in `adapter_bindings`, both managed by `repository.py:AdapterRepository`. Files in this directory become usable only after they are written to PostgreSQL with the service Root Key (`PUT /api/datasource/code`) and bound by a tenant administrator (`PUT /api/datasource`). Running pulls pin the revision current at acceptance; `worker.py` loads that revision and streams bounded batches on the Worker.

`_shared/` holds field mapping and builder helpers used by the agent files; `sources/` holds the Doris and Langfuse source implementations.

For multiple business Agents sharing one Langfuse project, copy `example-shared-langfuse.py` and set `SOURCE.trace_names` to 1–32 exact Trace names. `build_langfuse_adapter(SOURCE)` reads that list. Existing `build_langfuse_adapter(SOURCE, "one-name")` and `LangfuseSource(..., {"trace_name": "one-name"})` remain supported. Multiple names select their union. Names are literal strings, with no regular-expression or wildcard expansion.

The shared example exposes an optional `agent_id` field in the console. Leaving it empty includes all configured Trace names. Filling it selects the real Agent ID from `Trace.metadata.agent_id` or `Trace.metadata.teamevolver_execution.agent_id`. If both declarations exist, they must agree. This selection is applied during discovery, preview and detail fetches, including explicit Session lookups and scheduled Worker streaming. Existing user, tags, environment, version, release and metadata filters also apply to the fetched Traces. Tags require all requested values, metadata uses exact top-level values, and the other selection fields are combined with AND.

Time windows discover relevant Sessions. Detail fetches retain the full conversation for the selected Trace names and Agent, including earlier history, so incremental ingestion can preserve Context. Session IDs must identify actual conversations across the shared project. A real collaboration may keep one Session ID across Agents, while independent conversations use different IDs. Keep source-instance and project identities stable when changing the selected Agent.

Register the edited Python file in PostgreSQL, select its new immutable revision and save the tenant binding. The saved source and accepted filters determine a running job's selection. Connection credentials still come from the Worker's `LANGFUSE_PULL_HOST`, `LANGFUSE_PULL_PUBLIC_KEY` and `LANGFUSE_PULL_SECRET_KEY`, or the adapter's explicit environment-backed options. A registered file version does not freeze those process environment values.

Named connections reuse an adapter revision with separate versioned settings, filters and schedules. The service Root's Python file declares `SOURCE.connection_profiles`, with each group's fixed destination in `options` and credential handles in `secret_refs` or environment names in `env_refs`. `SOURCE.connection_options` lists ordinary editable fields such as `trace_names`. Operators select a declared group through `settings={"profile":"project_a","options":{"trace_names":["customer-turn"]}}`. The shared example accepts this resolved configuration through `build_adapter(config=None)`. Destination URLs, headers and credential references cannot be replaced through the operator settings.

Use `PUT /api/datasource/connections/{identity}` with `expected_revision` (0 to create), `adapter_id`, `adapter_revision`, `settings`, optional `label`, `enabled`, `default_filters` and the existing daily `schedule` shape. A fixed `default_filters.agent_id` cannot be widened by a temporary request. `GET /api/datasource/connections` lists connections, and `POST /api/datasource/connections/{identity}/pull`, `/test` and `/sessions` use the selected connection's frozen revision. `pull` and `sessions` accept timestamp fields plus optional `filters`; `test` accepts `{}`. The previous `/api/datasource` binding and schedule continue to provide the legacy default connection. Independent named connections use `datasource:<identity>` bindings and their own schedule/idempotency scopes.

Shared mapping extracts structured user IDs, titles, prompts and trace IDs, with provenance. Add source-specific interpretation in your Adapter hooks. Doris table names use `DORIS_TRACES_TABLE`, `DORIS_OBSERVATIONS_TABLE` and `DORIS_MAPPING_TABLE`; their columns must match the queries in `sources/doris.py`. Direct access requires `pymysql`; HTTP access requires an explicit `DORIS_PROXY_URL` and verifies TLS by default.

Endpoints, scheduled pulls and the CLI (`teamEvolver datasource --tenant ACCOUNT status|bind|test|list|pull`) are documented in [Session Ingestion and Data Source API](../../docs/en/api/03-session-ingest.md#data-source-adapters) and [Data Source Onboarding](../../docs/en/guides/10-datasource-onboarding.md).
