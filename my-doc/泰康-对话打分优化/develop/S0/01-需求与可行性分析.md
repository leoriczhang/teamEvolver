# S0 需求与可行性分析

日期：2026-11-09。本文保留设计时的可行性分析；当前落地状态见 [实现记录](04-S0实现与验证记录.md)。

## 1. 目标与业务边界

输入是一组已经由业务侧选定的优秀对话。输出回答三个问题：优秀表现是什么、通过哪些可观察动作体现、在什么情境适用。成果用于后续设计评分维度和行为档位，本阶段不计算新分数，也不从历史总分倒推出权重。

“优秀”是本次样本的选入条件，不意味着每句表达都应推广为规则。应从完整对话中识别有价值的行为；无明确增量的案例也可以完成分析并返回零条发现。不要为了覆盖而给每条记录硬造一个维度。

业务判断采用以下顺序：

1. 阅读完整对话，明确 HWP 的实际动作、客户提供的情境和随后回应。
2. 判断动作是否能迁移到类似情境，写出具体行为与条件。
3. 排除姓名、地点、数值替换及泛泛赞美等无独立方法价值的表述。
4. 保留不同情境下的适用差异，再进行同义归并。
5. 对无法确认的效果或权益事实作范围说明，不把代理人口头承诺提升为正式业务事实。

无需预置一套固定维度列表。章节与知识点用于组织分析范围，不直接决定最终维度数；可先形成知识点专项维度，再识别有证据支持的通用维度。只有一个案例支持的有价值行为也允许保留，标注证据范围即可。

输入采用字段白名单，默认仅保留：`课程名称`、`章节名称`、`知识点`、`场景名称`、`对话内容`。对练与实例 ID 只参与宿主生成稳定标识。

默认屏蔽五类反馈字段：`对练报告评分-中文`、`任务完成情况`、`最终得分`、`综合评价`、`改进建议`。仅屏蔽总分而保留既有评价，仍可能让模型复制历史判断，因此本版统一屏蔽。用户姓名、用户 ID、机构、客户编号、练习时长等元数据也不进入模型。

完整原始工作簿仍保留在受控来源中。模型只访问白名单生成的输入目录；禁止将原工作簿、带评价的通用转换表或完整宿主来源清单同时挂入本次 `from`。对话自身的字词、数字、人物称呼和不通顺表达不因字段屏蔽而改写。

## 4. OV 的分工边界

当前本机 OV 的 [Pipeline](../../../../../OpenViking/bot/vikingbot/compile/pipeline.py)依据 Skill 与执行指令规划；[agent_runner](../../../../../OpenViking/bot/vikingbot/compile/pipeline_agent.py)为每个 child 创建新消息历史、独立 scratch 和迭代预算。因此，Skill 可以控制单个 child 的业务职责，但宿主仍需控制每次 Compile 的输入集合。

[当前计划解析器](../../../../../OpenViking/bot/vikingbot/compile/plan.py)要求每种算子最多出现一次，Reduce 输出必须是文件。先前检查已验证当前默认 Skill 的“Reduce records＋第二次 Map”写法不兼容。S0 不复用这段计划，也不要求修改 OV。

新 Skill 的两个阶段均使用：

```python
files = p.map(sources, task=contract.extract)
p.finalize(files, into=target)
```

`contract.extract` 为 `execution=agent`、`input_unit=file`、`output=files`；这里的 Transform 名称不等同于业务 stage。提取阶段每个来源文件是一条完整案例；归并阶段每个来源文件是一个有界归并窗口。一个 child 只处理自己的文件，成功 emit 后结束。

公共 Compile API 的 `from` 必须为目录，不能把上述案例文件 URI 直接传入。
宿主为本次选中的完整文件建立独立有界目录并校验成员；文件 Map 将同一 URI 的
全部 ranges 按坐标交给一个 child。emit 使用 `FileResponse.files` 外壳，
业务 JSON 为其中的 content 字符串，inputs 为当前 assignment 的真实顶层 ID。
源码及服务核对依据见 [实现方案](02-实现方案与验收.md)。

这不是让一个 Compile 无限派生 Agent。TE 控制每次 Compile 的案例与窗口数、输入容量、同时在途的 Compile、回执和补偿；OV 负责该次 Compile 内的 child 执行。Planner 只规划当前有界输入，不承担全数据集扫描。

## 5. 从 llm-wiki 迁移的设计

参考[原始 llm-wiki Skill](../../../llm-wiki/SKILL.md)、[配置](../../../llm-wiki/OKF_CONFIG.yaml)和[大文件设计参考](../../../泰康-OV/S2/01-llm-wiki写法与大文件分析参考.md)。

| 参考方法 | 本需求的落实 |
| --- | --- |
| 判断写在主文，字段与边界集中配置 | 单个完整 Skill 内联优秀行为判断、阶段契约与字段规则，不加载隐藏附件 |
| 来源与执行指令分开 | 白名单案例是 Evidence；宿主 `instruction.stage` 才决定当前执行职责 |
| 按当前判断读取资源 | extract 只读 extract 契约；merge 只读 merge 契约，不将两个阶段长文复制到所有 Transform |
| 同范围同目的维护一份正文 | 同情境同观察目标的行为归并；条件不同不能靠标题相似直接合并 |
| 原文与派生结果分开 | 原文独立保存；归并输入为已定位的分析发现，不把分析文字变成合同事实 |

不迁移物流领域分类、Wiki frontmatter、页面角色、无需 coverage 的规则。参考目录缺少其所链接的 `scripts/check_output.py`，不能将该脚本当作已存在的验收实现。模板质量也不构成其大规模性能已被验证的证据。

## 6. 数据切分选择

### 6.1 两种格式各自承担什么

准备与交换格式为 UTF-8 JSONL，每行一条完整案例，换行字符在 JSON 字符串中转义。它适合流式读取、逐记录校验和后续大量数据导入。具体字段见[数据契约](03-数据契约与Skill设计.md)。

OV 执行输入为每案例一份 UTF-8 Markdown：元数据、完整对话和句级坐标分区保存。该选择与 `input_unit=file` 配合，使同一案例的所有 ranges 由同一个 child 处理，避免从一个大表行范围推断案例边界。

JSONL 不直接经过当前通用上传转换器：它未提供 `.jsonl` 转换支持。专用准备模块在 Worker 中读取交换格式，生成 Markdown，并通过现有 OV 内容写入接口冻结。宿主来源 manifest 不作为案例文件提交给 Map。

### 6.2 分批

S0 采用可配置的保守初值：

| 控制 | 初值 | 含义 |
| --- | --- | --- |
| 每次 extract Compile 案例数 | 最多 8 | 并行 child 的总量上限 |
| extract 输入字符数 / 字节数 | 最多 24,000 / 96,000 | 按最终 Markdown 序列化结果累加，两项均满足 |
| 单案例输入字符数 | 最多 20,000 | 超出转入容量待处理，不截断 |
| 单 merge 窗口成员数 | 最多 12 | observations 或已有维度定义合计 |
| 每次 merge Compile 输入字符数 / 字节数 | 最多 16,000 / 64,000 | 窗口大小按实际正文确定 |
| 在途 Compile | 默认 1，允许配置为 2 | 降低账号级 TPM 压力 |
| 单次工具/文件增量写入 | 建议 4,000 字符内 | 大结果分段写、最终按文件引用提交 |

这些是 TE 新任务的初始调度值，不是 OV 配额、模型 token 上限或性能保证。本机 OV [CompileLimits](../../../../../OpenViking/bot/vikingbot/compile/models.py)源码默认 `source_batch_chars=40,000`、`merge_input_chars=60,000`，运行配置可能不同。上线前核验实际部署可提供的配置；不能把源码默认当成当前运行值。

完整请求还包含 Skill、schema 和包装开销。准备阶段计算序列化输入容量，试运行观察实际请求与 429 / 上下文错误，按结果降低批次或并发；不为等待一项未知配额建立新的人工审批门槛。

### 6.3 大量数据

输入与输出都分片，PG 状态按执行单元保存；不在一个 job JSON 中保存所有对话、全部发现和所有案例映射。工作队列采用有界预取，默认准备最多两批待提交单元，具体存储见实现文档。

归并先按课程、章节、知识点建立工作分区，每个窗口保留完整行为定义与条件。S0 允许跨窗口近义维度并存，记录告警；不强制把全部维度压入最后一个全局 Reduce。后续补偿任务可按有界窗口合并近义维度，但合并必须由模型明确提交成员关系。

已有维度不允许为了装入窗口而删减业务定义。单项定义超过容量时保留原文件与问题，扩大该单元预算或单独处理。全部维度无需缩减到 12 个；12 是窗口容量。

## 7. 原文定位与可选引文

默认保留句级 `sentence_refs`，用于定位案例发现及后续人工查验。默认不输出长引文 `quote`，也不要求每个维度复制案例原话。

选择句级定位的原因是维度需要能回到实际行为，同时让验收代码确定性判断引用是否存在。它不要求全文逐句打标，也不把每个句子都提炼为发现。

如模型主动输出或后续用户要求输出 `quote`，执行以下强制规则：

> 不能因为引文长用省略号代替。不能因为语句不通、多字或少字删掉原文。引用必须和原文一致。

引用单位为一个或多个完整、连续的句级跨度；断开的原话用多个引用表达，不拼接成一段。原文自身包含的省略号、错字和口语重复必须保留，不能用“检测到省略号”直接判错。

坐标错误但文本在当前案例中唯一精确匹配时，可确定性重定位；改写、删字、添加替换字的引文不能用模糊匹配修成“通过”。此类问题只隔离相关引用或发现，不默认让整批失败。

## 8. 宽松验收原则

验收检查“数据是否可信地对应输入、运行是否完成、结果是否可消费”。文案质量和业务成熟度与技术完成分别展示。

小问题包括标题不够好、维度稍宽、通用/专项分类不理想、近义重复、只有一个案例、可选说明缺失。这些都不作为失败门槛，保留结果和告警即可。

无法精确定位的引用、凭空出现的案例 ID、不可确认的局部承诺，隔离到条目并保留原始提交。已完成案例可以以 `analyzed_with_issues` 返回；受影响发现标记 `needs_review`，不宣称已验证，但其余结果继续交付。

没有分析回执的案例属于运行未完成，保留 `pending`，不能用“没有优秀表现”替代。少量未完成时保留已完成制品，可继续补偿，但对外不能声称全量完成。输入丢失、路径越界、不可恢复的 JSON、冒用来源版本等大问题阻断受影响单元。

## 9. S0 的交付界限

本版产出新的编译 Skill、专用输入准备、阶段调度、宽松验收代码和可查看的结构化结果。基础任务可在现有 API 受理和预览链路使用，完整工作台交互不是 S0 必需项。

不要求每条对话一个维度，不要求固定维度数量、12 个验证案例、逐维度打分、权重求解或业务专家审批。新编译 Skill 是执行工具，其输出是分析制品；本阶段不创建、验证或发布团队 Skill Candidate。

S0 成功标志是：171 条现有案例全部有真实提取回执；出现的问题能够定位、隔离或补偿；通过接受的发现形成可消费的维度分片；大量输入的计划、调度和恢复不会将全部正文集中到一个 Agent。
