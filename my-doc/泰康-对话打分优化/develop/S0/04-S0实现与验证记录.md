## 1. 实现范围

沿用原有界面与任务 API。用户在编译指令界面保存完整 Skill，正文中的
`te-dialogue-dimensions.v1` 声明选择对话维度执行；后端不覆盖用户正文。
初版仅使用一个 SKILL.md，包含 extract / merge 指令与字段契约；
不使用隐藏附件、独立 compiler_body_snapshot 或新增任务模式参数。

已实现：

- XLSX / JSONL 白名单导入、逻辑标识与业务正文版本、完整对话 Markdown、Unicode 句级坐标。
- 按条数、完整序列化字符和 UTF-8 字节联合分批，超容量案例保持待处理，不拆对话。
- 每单元独立 Compile，PG 分页计划与回执，先持久化提交意图、再用原键对账；
  POST 回执丢失不换键重发。使用现有 Worker、租约及租户共享 Compile 槽。
- 每次提交建立独立输入目录，完整复制本批未接受案例或当前窗口，校验摘要及目录成员，
  Compile.from 传目录；源与目标互不嵌套。明确 HTTP 请求拒绝保留脱敏原因，
  停止其他批次自动提交；未知受理状态继续以原键对账。
- 保留成功 child，只补偿缺失/无效案例。提取后按知识点及容量建立有限窗口；
  归并只使用显式成员关系，不自行按标题相似合并，不要求减少维度数。
- JSON 外壳确定性修复、可选字段默认值、局部发现/引文隔离。有效原文定位可生成宿主恢复文本；
  错误提交保留在 issues，不静默冒充精确引文。
- 分片发现、维度、案例映射、coverage、issues、validation、manifest 及现有制品预览投影。
- 显式恢复部分交付时复用已接受案例；内容完全相同的归并窗口也复用成功回执，
  新交付独立归档，保持原交付不被覆盖。
- 原有“从断点恢复”按钮为对话任务携带稳定 request_id；丢回包重试复用同一键，
  恢复 epoch 清除旧请求与拒绝标记。没有新增恢复按钮。
- `POST /api/mining/dialogue-datasets` 后台准备入口与原有 `POST /api/mining/jobs`，
  Router 不执行 XLSX 处理或 Compile。任务只需要所选知识源和原有参数。

生产实现位于 [dialogue_dimensions](../../../../team_miner/skill_miner/dialogue_dimensions/)、
[新 Skill 包](../../../../team_miner/skill_miner/compiler_skills/dialogue-dimensions-v1/)。
项目 API 详情已同步至中英文文档，并重新生成端点索引。

### 本轮 OV 契约修正验证

先前宿主 fake 直接读取文件 URI，没有执行 OV 的目录前置校验，所以上述测试通过不能证明
Compile 请求符合服务契约。本轮 fake 改为只接受目录，并覆盖目录成员污染、原文完整复制、
永久拒绝只 POST 一次、拒绝原因脱敏与输出、恢复清除拒绝状态、只补缺失案例，
以及原恢复按钮在丢回包后复用 request_id。

另在安装的 OV 解释器中实际执行其 `CompileRequest`、`CompileService._normalize_request`、
`EntryResponse`、`parse_plan`、文件 Map 的 `run`、`FileResponse`、
`validate_files` 和 `validate_input_refs`。目录请求通过、文件请求拒绝、
一次 Map / Finalize 通过、同一 URI 的全部 ranges 按坐标归组、JSON 文件外壳通过、
业务 ID 冒充输入 ID 拒绝。此验证使用 stat 与 child 替身，只隔离外部依赖，
未调用 LLM、未修改 OV 文件；不能声称模型已正确产出真实业务 JSON。

真实 OV HTTP 预检使用生产 `stage_inputs` 和 deferred write，把一条合成案例完整写入独立目录；
stat 返回 `isDir=true`。同一文件 URI 的 Compile 请求返回目录校验 400；
目录 URI 的请求通过来源校验，在故意设置的不存在 Skill 处返回 404。
两者均在创建 task 前结束，Compile 受理数及 LLM 调用数为 0，
没有恢复或重新创建用户业务任务。证据见 [OV 契约预检结果](05-OV契约预检结果.json)。

本轮真实隔离 PG、对话、架构与文档契约合计 68 项通过；
完整前端 260 项通过，生产构建通过，文档引用 104 个文件、830 处引用无错误或告警。
全量 Python 后续完成：2133 项通过、192 项跳过；Ruff 全项目检查通过。

## 4. 初步版本限制与测试方式

本版初次业务分析固定 `max_rounds=1`；多批次照常完成，不受单轮数量限制。
新数据、修改容量、不同业务修订使用新任务。恢复支持复用已确认的案例与完全相同的窗口，
尚未实现跨新数据任务的自动全局发现缓存或既有维度增量更新。

`max_inflight_compiles` 可配置 1–2，当前调度器使用串行提交，2 是允许的上限，
并未实现同任务同时两条 Compile 的吞吐优化。归并限于有界知识点窗口，跨窗口近义重复允许交付，
不执行无限归并。没有新增交互式维度浏览器。

API 原文件准备上限 20 MiB，超出时先用本地流式准备工具导出并上传，再用 OV URI 创建任务。
清单分页，单元状态独立持久化，结果按完整记录分片；任务预览仍复用现有 PG 文件快照/缓存机制，
超大规模的快照恢复性能尚未通过真实数据压测验证。

重启本项目 API 和 Worker 后使用原有流程：在编译指令编辑器保存
[完整主体 Skill](../../../../team_miner/skill_miner/compiler_skills/dialogue-dimensions-v1/SKILL.md)，
选择已登记的 171 条 model_cases 来源，通过原有创建任务按钮启动。
旧部分交付可通过原有“从断点恢复”按钮补处理，仍使用受理时的配置正文；
要使用修改后的 Skill 正文应保存后新建任务。OV 不需修改或重启。
本轮没有自动恢复用户任务或启动新的付费业务挖掘，未生成或发布 Skill Candidate。

## 5. v2 能力维度与候选评分口径适配

依据用户 [v2 原稿](../../data/SKILL.md) 更新本地主体 Skill，保留独立目录输入、真实 assignment
输入 ID、Entry 与文件 Map 的 FileResponse 外壳、临时 `content_ref` 等运行契约。
业务规则区分能力维度、行为指标和方法实例；评分口径只在现有维度 `notes` 中交付，不实际评分。

宿主只对显式 `groups` 生成确定性维度 ID 与案例关联。`kept_separate` 不再用成员标题、动作
自动生成维度；与 `deferred` 一起保留具体方法、条件、案例版本、句子和原文坐标，以及
`disposition` 与原因，写入原有 `issues/merge-*.jsonl` 分片并纳入交付清单。
成员全部独立保留、零维度也允许完整交付；单例 group、缺评分口径或 `rubric_pending` 不阻断。

本轮定向测试 22 项通过、1 项 PG 测试因未配置隔离数据库跳过；全项目 Ruff 通过。
覆盖独立方法不变维度、保留来源、单例维度、候选口径原样交付、待校准与缺口径容忍，
以及 20 条全链路零维度成功交付和断点恢复。
